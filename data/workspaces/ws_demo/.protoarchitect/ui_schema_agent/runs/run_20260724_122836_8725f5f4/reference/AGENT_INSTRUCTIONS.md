# UI Schema synchronization agent

Ты синхронизируешь логическую UI-схему ProtoArchitect со всеми требованиями из `/input/requirements.json`.

## Рабочие файлы

- `/input/task.json` — параметры запуска и комментарии аналитика;
- `/input/requirements.json` — полный файл требований текущего запуска;
- `/reference/STORAGE.md` — формат хранения UI-схемы;
- `/reference/config.yaml` — единый каталог типов UI-элементов;
- `/working/ui_schema/` — временная копия UI-схемы, которую можно изменять;
- `/scratch/` — план и промежуточные материалы;
- `/result/agent_report.json` — обязательный итоговый отчёт.

## Порядок работы

1. Прочитай `task.json`, этот документ, `STORAGE.md` и `config.yaml`.
2. Изучи текущую UI-схему целиком: приложение, меню, страницы, элементы и связи.
3. Изучи весь файл требований до начала изменения схемы.
4. Составь план в `/scratch/plan.md`:
   - существующие и новые страницы;
   - общие элементы приложения и меню;
   - логические группы требований;
   - предполагаемые изменения связей.
5. Последовательно синхронизируй схему с требованиями.
6. Проведи финальный проход по каждому входному requirement id.
7. Запиши итоговый отчёт.
8. Вызови `validate_ui_schema` и исправь обнаруженные структурные ошибки.

## Правила изменения схемы

- Существующая схема является действующей архитектурной основой.
- Сохраняй подходящие страницы, элементы, стабильные идентификаторы и связи.
- Не перестраивай структуру без необходимости.
- Отсутствие требования во входном файле не означает, что существующий объект или связь нужно удалить.
- Одно требование может быть связано с несколькими UI-объектами.
- Один UI-объект может быть связан с несколькими требованиями.
- Создавай трассировку до конечного UI-элемента, когда это возможно.
- Если требование относится к странице в целом, допустима связь со страницей.
- Не добавляй `route`, `layout`, frontend-компоненты, CSS-классы или framework-specific поля.
- Не изменяй `requirements.json`, `code_links.json` и `index.json`.
- Для удаления устаревшего файла страницы используй только инструмент `delete_ui_schema_page_file`.

## Результаты анализа требований

Для каждого требования должен существовать один из результатов:

- связь хотя бы с одним UI-объектом;
- `no_ui` — отдельный UI-объект не требуется;
- `unclear` — информации недостаточно для уверенного решения.

Не создавай фиктивные UI-элементы только ради покрытия требования.

## Формат `/result/agent_report.json`

```json
{
  "summary": "Краткое описание результата синхронизации.",
  "no_ui": [
    {
      "requirement_id": "REQ-0001",
      "reason": "Причина отсутствия отдельного UI-объекта."
    }
  ],
  "unclear": [
    {
      "requirement_id": "REQ-0002",
      "reason": "Каких данных не хватает."
    }
  ],
  "warnings": [
    "Необязательные замечания для аналитика."
  ]
}
```

Не включай в отчёт внутренние рассуждения или полный журнал работы.
