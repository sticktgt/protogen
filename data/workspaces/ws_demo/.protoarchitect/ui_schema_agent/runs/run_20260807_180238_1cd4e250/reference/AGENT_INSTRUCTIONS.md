# Управляемый pipeline синхронизации UI Schema

Этот документ описывает архитектуру управляемого pipeline и границы ответственности. Нормативные задачи модели находятся только в отдельных prompt-файлах, а параметры выполнения — только в `modules/ui_schema/config.yaml`.

## Совместимые внешние контракты

Pipeline сохраняет:

- формат входного JSON-набора требований;
- каноническую структуру `<workspace>/ui_schema/`;
- формат `mappings/requirement_ui_links.json`;
- формат preview, экспорта и применения результата.

Совместимость со старой внутренней state machine, coverage plan, batch tools и review tools не является контрактом.

## Этапы

### 1. Анализ

Backend механически делит требования по `agent.pipeline.analysis_batch_size`. Каждый LLM-вызов получает только одну группу и возвращает полный семантический результат для её ID.

Prompt: `pipeline_analysis.md`.

### 2. Проектирование и применение

Требования делятся по `agent.pipeline.planning_batch_size`. Каждый вызов получает:

- требования и анализ текущей группы;
- компактный анализ полного набора для согласования общих решений;
- фактическую текущую UI-схему и прежнюю трассировку;
- вычисляемый плоский технический индекс существующих страниц и элементов с типами, родителями и допустимыми действиями;
- список requirement ID уже завершённых групп.

Модель возвращает решения только текущей группы и один транзакционный пакет. Перед применением backend без изменения файлов собирает все объективно определимые ошибки решений и операций: существование целей, родителей, scope, типы и UI-связи. Если пакет отклонён, repair получает структурированный полный список ошибок, только затронутые страницы, локальные связи и технический индекс этих объектов. После успешного применения следующий пакет видит обновлённую схему.

Prompts: `pipeline_planning.md`, при техническом отклонении — `pipeline_repair.md`.

### 3. Аудит

После всех пакетов свежие изолированные вызовы проверяют только решения `direct_ui` и фактический UI. Для каждой заявленной цели передаётся компактный плоский outline самой цели и её потомков, а также связанные `ui_links`; целиком незатронутые страницы в audit-контекст не включаются. `cross_cutting_ui` и `no_ui` сохраняются в итоговой трассировке, но повторно смысловым audit не проверяются. Audit не перепроверяет исторический выбор `create/reuse/extend`: его задача — убедиться, что явно перечисленные в `direct_ui`-требовании поля, действия, состояния, шаги и переходы представлены минимально достаточным прототипом. Аудит возвращает только реальные дефекты и выполняется до перехода к коррекции.

Prompt: `pipeline_audit.md`.

### 4. Коррекция

Requirement ID с дефектами или отсутствующими целями делятся по `agent.pipeline.correction_batch_size`. Модель получает только соответствующие требования, решения, ошибки и текущую схему. Каждый пакет применяется транзакционно. Выполняется один correction-раунд, после которого повторный аудит проверяет только исправлявшиеся требования. Оставшиеся смысловые замечания становятся предупреждениями для ручной проверки.

Prompt: `pipeline_correction.md`.

### 5. Структурная проверка

Backend сравнивает базовую и рабочую схему и собирает ограниченный список локальных кандидатов: пустые новые или обещанные к расширению контейнеры, существующие контейнеры, опустошённые текущим запуском, новые элементы вне предполагаемого ID-контейнера, self-navigation, несколько безусловных целей навигации и созданные целевые страницы без входящей навигации. На этом этапе модель не вызывается и схема не меняется. Высокосигнальные кандидаты сохраняются в диагностике и выводятся как предупреждения для ручной проверки.

### 6. Экспорт и validation

Backend преобразует канонические решения модели в requirement links и `agent_report.json`, выполняет существующую структурную validation и создаёт preview.

## Изоляция вызовов

Каждый этап вызывает модель отдельным пользовательским сообщением. Основной канал результата — один минимальный output tool с аргументом `payload`; для OpenAI-совместимых транспортов, которые не возвращают tool call, принимается точный JSON-объект по той же схеме. История предыдущих LLM-обменов не передаётся. Авторитетное состояние находится в JSON-файлах запуска и фактической `working/ui_schema/`.

Модель не выбирает tool, stage, batch ID или recovery-маршрут. Backend не запускает автономный agent loop. Защитный лимит времени запрещает запуск следующего LLM-вызова, но не отбрасывает уже полученный ответ: завершённый вызов разбирается и применяется, чтобы не терять оплаченный результат.

## Граница backend

Backend может:

- формировать механические группы;
- загружать prompt-файлы и конфигурацию;
- вызывать фиксированный этап;
- проверять Pydantic/JSON-формат и полноту ID;
- строить вычисляемый технический индекс канонической схемы без изменения формата хранения;
- проверять существование точной пары `target_type`/`target_id`;
- до применения пакета агрегировать объективные ошибки scope, типов, родителей, уникальности ID и допустимых связей;
- транзакционно применять явно переданные операции;
- записывать канонические файлы хранения, diff и диагностику.

Backend не может:

- анализировать текст требования;
- назначать `ui_effect` или классификацию;
- выбирать подходящий объект схемы;
- решать, какие поля, действия, состояния или сообщения нужны пользователю;
- исправлять смысловое решение модели;
- выводить `implementation_status` из структуры.

Проверки сочетаний полей являются только проверкой возможности сохранить решение: например, `no_ui` не может одновременно содержать прямую UI-цель.

## Промпты и параметры

Prompt-текст не хранится в Python-коде. Карта стадий, имена prompt-файлов, имена output tools, размеры групп и число попыток находятся в `config.yaml`.

Текущие роли:

```text
pipeline_analysis.md
pipeline_planning.md
pipeline_repair.md
pipeline_audit.md
pipeline_correction.md
```

Общие правила формирования и технического исправления `changes`-пакетов находятся в `pipeline_change_rules.md` и подключаются к planning, repair и correction. Ролевые prompt-файлы не должны копировать эти правила или противоречить им.

Prompt-файлы не должны дублировать управление pipeline. Каждый ролевой файл описывает только одну роль и один формат результата.

## Транзакционность и сохранение существующих объектов

Операции группы применяются атомарно. Перед записью выполняется не изменяющая файлы техническая проверка всего пакета. При ошибке рабочая схема остаётся в состоянии до текущего пакета; ранее успешные группы сохраняются. Исправление повторяет только отклонённый пакет и получает локальный контекст его зависимостей.

Для существующей страницы метаданные изменяются через `update_pages`. Для существующего ID элемента родитель сохраняется, если модель не передала явное перемещение. Переиспользование и расширение требуют реально существующей точной цели. Создание требует отсутствующей цели, которая появляется в текущем пакете.

Planning и correction не удаляют UI-объекты и UI-связи. Структурная проверка также ничего не изменяет: найденные кандидаты только сохраняются в диагностике и выводятся как предупреждения.

## Диагностика

Временный запуск сохраняет:

- анализ требований;
- применённые planning-пакеты;
- найденные audit issues;
- correction-пакеты;
- финальные канонические решения;
- состояния pipeline, события, метрики и validation.

Диагностический архив содержит снимки prompt-файлов и их SHA-256, но не credentials и не внутренние рассуждения модели.
