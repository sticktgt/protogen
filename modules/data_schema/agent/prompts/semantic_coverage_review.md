Проведи проверку покрытия требований. Верни не более {max_issues} сгруппированных замечаний.

Двигайся только от требований к схеме и итоговой трассировке. В контексте требования технически разложены по текущему результату агента в `requirements.by_current_result`; это не оценка backend и не доказательство корректности classification.

Контекст содержит только текущий пакет синхронизации. Он может быть неполной частью общего набора требований. Не считай отсутствующие requirement ID удалёнными и не создавай замечания к унаследованной трассировке вне текущего пакета.

Проверяй в таком порядке:

1. Полностью проверь `no_data`.
   - `no_data` допустимо только когда требование можно выполнить без предметных данных.
   - UI-формулировка сама по себе не делает требование `no_data`.
   - Если подходящие объекты и поля уже существуют, ошибочная `no_data` или отсутствующие links являются `advisory`: рекомендуй заменить classification на `direct` и добавить минимальные links.
   - Если требование задаёт существенный повторяемый объект или явно перечисляет основные сохраняемые характеристики, которых в схеме негде хранить, это `must_fix`.

2. Проверь `cross_cutting_data` и `unclear`.
   - `cross_cutting_data` допустимо только для сквозного правила данных без конечного набора targets.
   - `unclear` допустимо только когда без предположений нельзя выбрать представление данных.

3. Проверь `direct`.
   - Проверь наличие прямо требуемых основных объектов, сохраняемых характеристик и управляемых наборов.
   - Проверь, что выбранная конструкция способна хранить явно перечисленные характеристики.
   - Проверь существенные связи. Отсутствующая связь является `must_fix` только когда без неё нельзя определить центральную принадлежность или результат; дополнительная связь между уже существующими записями — `advisory`.
   - Неполные или неточные links являются `advisory`, если сама структура уже приемлемо выражает требование.

Общие ограничения:

- не требуй хранимые поля для данных, прямо описанных как вычисляемые или показываемые для выбранного периода;
- не расширяй модель сверх требований;
- не рекомендуй значения справочника, если конкретные значения не перечислены;
- значение dictionary имеет только `id`, `title`, `description`; если нужны другие атрибуты, фиксируй неверный тип конструкции;
- не анализируй общую красоту и единообразие схемы.

Группируй ошибки с совместимым итоговым исправлением. Ошибочные classifications с уже существующей структурой объединяй в advisory. Отсутствующую основную структуру группируй по одному объекту или одной конструкции. Не повышай проблему до `must_fix` только ради автоматической коррекции.

Для этого режима `verified_issue_ids=[]`. Установи `coverage_complete=true` только после проверки каждого требования во всех группах.
