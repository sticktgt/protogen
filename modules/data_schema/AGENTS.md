# AGENTS.md — модуль `data_schema`

Документ предназначен для LLM-агентов и разработчиков, которые дорабатывают модуль `data_schema` в ProtoArchitect.

## Назначение модуля

`data_schema` — модуль логической схемы данных прототипа.

Модуль нужен для описания данных предметной области на уровне, пригодном для аналитика, LLM и последующей генерации прототипа. Он хранит сущности, поля, справочники, логические связи и трассировку к требованиям, UI, API и коду.

Модуль не описывает физическую реализацию хранения. Не добавлять в логическую схему SQL-таблицы, SQL-колонки, SQL-типы, индексы, миграции, ORM-маппинги, настройки PostgreSQL/MySQL/JSON-хранилища, транзакции, права доступа и бизнес-поведение.

## Где находится модуль

```text
backend/modules/data_schema/
frontend/modules/data_schema/
modules/data_schema/
data/workspaces/<workspace_id>/data_schema/
```

Назначение папок:

| Папка | Назначение |
| --- | --- |
| `backend/modules/data_schema/` | FastAPI API, операции со схемой, чтение и запись JSON. |
| `frontend/modules/data_schema/` | HTML/CSS/JS интерфейс модуля. |
| `modules/data_schema/` | manifest, config, OpenAPI, interop, README, AGENTS, docs и init-шаблон. |
| `data/workspaces/<workspace_id>/data_schema/` | Рабочие данные схемы конкретного workspace. |

## Структура хранения

Рабочие данные модуля находятся в:

```text
<workspace>/data_schema/
```

Актуальная структура:

```text
data_schema/
  schema.json
  index.json
  entities/
    <entity_id>.json
  relations.json
  dictionaries.json
  mappings/
    requirement_data_links.json
    ui_data_links.json
    api_data_links.json
  code_links.json
  requirements.json
```

`schema.json`, `entities/*.json`, `relations.json`, `dictionaries.json`, mapping-файлы и `code_links.json` являются основными файлами схемы. `index.json` является производным индексом и не редактируется вручную.

`requirements.json` может использоваться как локальный источник требований для демонстрации и трассировки. Модуль `data_schema` не должен редактировать требования как бизнес-данные. Связи с требованиями используют `requirements[].id`.

Подробный формат файлов описан в `modules/data_schema/docs/STORAGE.md`.

## Init-шаблон и демо-данные

Init-шаблон для нового workspace находится в:

```text
modules/data_schema/init/
```

В `init/` должны быть только пустые файлы минимальной структуры. Не добавлять туда демо-сущности, демо-поля, демо-связи или реальные требования.

Демо-схема допустима только в конкретном workspace, например:

```text
data/workspaces/ws_demo/data_schema/
```

## Идентификаторы

ID сущностей, полей и связей между сущностями формируются backend автоматически из названия.

Frontend не должен требовать ручного ввода ID при создании сущности, поля или связи.

LLM при создании объекта через API должна передавать `title` и использовать `id`, который вернул API. Не нужно заранее придумывать ID, кроме случаев прямого редактирования файлов.

Правила ID описаны в `modules/data_schema/docs/STORAGE.md`.

## Логические типы данных

Поддерживаемый перечень типов:

```text
string
text
integer
decimal
boolean
date
datetime
uuid
dictionary
json
```

Тип поля является логическим. Он не является SQL-типом.

Если добавляется новый тип данных, необходимо обновить:

```text
backend/modules/data_schema/entity_ops.py
frontend/modules/data_schema/js/data-types.js
modules/data_schema/docs/STORAGE.md
```

Если меняется API создания или обновления поля, также обновить:

```text
backend/modules/data_schema/API.md
modules/data_schema/api.openapi.yaml
```

## Backend

Основные файлы backend:

| Файл | Назначение |
| --- | --- |
| `api.py` | FastAPI routes. |
| `schemas.py` | Pydantic-модели request payload. |
| `storage.py` | Пути файлов модуля, чтение и запись JSON, fallback-структуры. |
| `files.py` | Низкоуровневое чтение и запись JSON. |
| `ids.py` | Генерация человекочитаемых идентификаторов. |
| `entity_ops.py` | Операции со схемой, сущностями и полями. |
| `relation_ops.py` | Операции со связями между сущностями. |
| `link_ops.py` | Операции со связями требований, UI, API и кода. |
| `index_builder.py` | Пересборка `index.json`. |
| `summary.py` | Агрегированная выдача для frontend. |
| `service.py` | Фасад для API. |

Правила backend-разработки:

- не раздувать `api.py` бизнес-логикой;
- не раздувать `service.py`, он должен оставаться фасадом;
- операции с сущностями и полями держать в `entity_ops.py`;
- операции со связями сущностей держать в `relation_ops.py`;
- операции с requirement/UI/API/code links держать в `link_ops.py`;
- после изменения структуры схемы пересобирать `index.json`;
- использовать `pathlib`, не использовать платформозависимые пути;
- не добавлять физические storage-мэппинги в backend модуля.

## Backend API

Префикс API:

```text
/api/data-schema
```

Человекочитаемое описание API находится в:

```text
backend/modules/data_schema/API.md
```

Машинно-читаемое описание:

```text
modules/data_schema/api.openapi.yaml
```

Все POST/PUT payload должны содержать `workspace_id`. GET/DELETE используют `workspace_id` как query-параметр.

Другие модули должны использовать API, а не читать файлы `data_schema` напрямую, если им нужно работать с текущими данными схемы в runtime.

- code links в текущем UI только отображаются.

## UI модуля

Основные представления:

```text
Карта данных
Структура сущности
Граф JointJS
```

### Карта данных

Показывает карточки сущностей. В карточке выводятся первые поля, признак скрытых полей и краткий список связей сущности с другими сущностями. На карте есть фильтр по названию и ID сущности.

Клик по сущности открывает `Структура сущности`. Клик по связи в карточке сущности открывает `Структура сущности → Связи`.

### Структура сущности

Основной редактор. Слева список сущностей с фильтром, справа редактор сущности или поля.

Порядок вкладок:

```text
Поля
Связи
Требования
UI
API
Код
```

Удаление сущности или поля показывается только на вкладке `Поля` рядом с сохранением.

### Граф JointJS

Экспериментальное представление поверх JSON-схемы. Граф не является источником истины.

Правила графа:

- одинарный клик по сущности или связи выделяет объект и показывает свойства;
- двойной клик по сущности открывает редактор сущности;
- двойной клик по связи открывает вкладку `Связи`;
- координаты узлов и выбранный объект не сохраняются в логической схеме;
- если библиотека JointJS недоступна, модуль должен показать понятное сообщение, не ломая остальные вкладки.

## Связи с требованиями

Связи хранятся в:

```text
data_schema/mappings/requirement_data_links.json
```

Связь указывает на `requirements[].id`.

В UI связывание выполняется через фильтруемый список требований. В карточке требования показывать доступные признаки: группа, тип, статус, приоритет.

Пока нет отдельного модуля требований, источник требований может быть локальным `requirements.json` внутри `data_schema`.

## Связи с UI-схемой

Связи хранятся в:

```text
data_schema/mappings/ui_data_links.json
```

Основной способ выбора UI-объекта в интерфейсе — через API модуля `ui_schema`: выбор страницы, иерархия элементов, фильтр по типу элемента и текстовый фильтр.

Ручной ввод ID UI-элемента не является основным способом работы аналитика.

## Связи с API-схемой

Связи хранятся в:

```text
data_schema/mappings/api_data_links.json
```

API-схема как отдельный модуль пока не реализована. Текущий формат links уже предусматривает связь с API-ресурсом, операцией, DTO, параметром или другим API-объектом.

## Связи с кодом

Связи хранятся в:

```text
data_schema/code_links.json
```

В текущем UI связи с кодом только отображаются. Не добавлять ручное создание code links в UI без отдельного решения.

Наличие API для `code-links` не означает, что модуль генерирует код. Генерация кода не является задачей `data_schema`.

## Что не менять без отдельного решения

Не менять без явного требования:

```text
логический характер схемы данных;
отсутствие физического storage-мэппинга;
структуру <workspace>/data_schema/;
правило один файл на сущность;
формат field target_id как <entity_id>.<field_id>;
перечень поддерживаемых типов данных;
порядок вкладок редактора;
принцип, что index.json является производным файлом;
принцип, что JointJS-граф не хранит логическую модель;
отсутствие ручного добавления code links через UI.
```

## Правила для LLM-агента

При доработке модуля:

1. Определить, меняется ли структура хранения, API, backend-логика, frontend UI или документация.
2. Если меняется структура JSON-файлов, обновить `modules/data_schema/docs/STORAGE.md`.
3. Если меняется API, обновить `backend/modules/data_schema/API.md` и `modules/data_schema/api.openapi.yaml`.
4. Если меняются связи с другими модулями, обновить `modules/data_schema/interop.yaml`.
5. Если меняется назначение, возможности или структура интерфейса, обновить `README.md`.
6. Если меняются правила доработки или архитектура модуля, обновить `AGENTS.md`.
7. Не добавлять физические особенности хранения в схему данных.
8. Не добавлять демо-данные в `modules/data_schema/init/`.
9. Не редактировать `index.json` вручную.
10. Не создавать большие JS/Python-файлы; декомпозировать по ответственности.
11. Не использовать ручной ввод ID как основной пользовательский сценарий создания объектов.
12. Сохранять схему понятной аналитику и пригодной для обработки LLM.
