# AGENTS.md — модуль `data_schema`

Документ предназначен для LLM-агентов и разработчиков, которые дорабатывают модуль `data_schema` в ProtoArchitect.

## Назначение модуля

`data_schema` — модуль логической схемы данных прототипа.

Модуль нужен для описания данных предметной области на уровне, пригодном для аналитика, LLM и последующей генерации прототипа. Он хранит сущности, поля, справочники, логические связи и трассировку к требованиям, UI, API и коду.

Модуль не описывает физическую реализацию хранения. Не добавлять в логическую схему SQL-таблицы, SQL-колонки, SQL-типы, индексы, миграции, ORM-маппинги, настройки PostgreSQL/MySQL/JSON-хранилища, транзакции, права доступа и бизнес-поведение.

## Структура хранения

Рабочие данные модуля находятся в:

```text
<workspace>/data_schema/
```

Актуальная структура:

```text
data_schema/
  schema.json
  index.json
  entities/
    <entity_id>.json
  relations.json
  dictionaries.json
  mappings/
    requirement_data_links.json
    ui_data_links.json
    api_data_links.json
  code_links.json
  requirements_source.json
```

`schema.json`, `entities/*.json`, `relations.json`, `dictionaries.json`, mapping-файлы и `code_links.json` являются основными файлами схемы. `index.json` является производным индексом и не редактируется вручную.

`requirements_source.json` содержит workspace-relative ссылку на выбранный файл требований другого модуля. Файл содержит актуальный полный набор требований, готовых на момент запуска; в следующих итерациях он может быть дополнен или изменён. `data_schema` читает требования, но не редактирует их как бизнес-данные. Связи используют `requirements[].id`. Унаследованные связи на ID, отсутствующие в актуальном наборе, сохраняются и выводятся аналитику для ручной проверки. Legacy `requirements.json` допускается только для чтения старых workspace без файла ссылки.

Подробный формат файлов описан в `modules/data_schema/docs/STORAGE.md`.

## Init-шаблон и демо-данные

Init-шаблон для нового workspace находится в:

```text
modules/data_schema/init/
```

В `init/` должны быть только пустые файлы минимальной структуры. Не добавлять туда демо-сущности, демо-поля, демо-связи или реальные требования.

Демо-схема допустима только в конкретном workspace, например:

```text
data/workspaces/ws_demo/data_schema/
```

## Идентификаторы

ID сущностей, полей и связей между сущностями формируются backend автоматически из названия.

Frontend не должен требовать ручного ввода ID при создании сущности, поля или связи.

Для ручного UI/API сценария можно передать `title` и использовать ID, сформированный backend. Встроенный LLM-агент работает по более строгому контракту: для каждого нового объекта он обязан явно передать короткий осмысленный английский `snake_case` ID, чтобы межмодульные контракты не зависели от транслитерации локализованного title. Существующие ID агент сохраняет.

Правила ID описаны в `modules/data_schema/docs/STORAGE.md`.

## Backend

Основные файлы backend:

| Файл | Назначение |
| --- | --- |
| `api.py` | FastAPI routes. |
| `schemas.py` | Pydantic-модели request payload. |
| `storage.py` | Пути файлов модуля, чтение и запись JSON, fallback-структуры. |
| `files.py` | Низкоуровневое чтение и запись JSON. |
| `ids.py` | Генерация человекочитаемых идентификаторов. |
| `entity_ops.py` | Операции со схемой, сущностями и полями. |
| `relation_ops.py` | Операции со связями между сущностями. |
| `link_ops.py` | Операции со связями требований, UI, API и кода. |
| `index_builder.py` | Пересборка `index.json`. |
| `summary.py` | Агрегированная выдача для frontend. |
| `service.py` | Фасад для API. |

Правила backend-разработки:

- не раздувать `api.py` бизнес-логикой;
- не раздувать `service.py`, он должен оставаться фасадом;
- операции с сущностями и полями держать в `entity_ops.py`;
- операции со связями сущностей держать в `relation_ops.py`;
- операции с requirement/UI/API/code links держать в `link_ops.py`;
- после изменения структуры схемы пересобирать `index.json`;
- использовать `pathlib`, не использовать платформозависимые пути;
- не добавлять физические storage-мэппинги в backend модуля.

## Backend API

Префикс API:

```text
/api/data-schema
```

Человекочитаемое описание API находится в:

```text
backend/modules/data_schema/API.md
```

Машинно-читаемое описание:

```text
modules/data_schema/api.openapi.yaml
```

Все POST/PUT payload должны содержать `workspace_id`. GET/DELETE используют `workspace_id` как query-параметр.

Другие модули должны использовать API, а не читать файлы `data_schema` напрямую, если им нужно работать с текущими данными схемы в runtime.

## UI модуля

Основные представления:

```text
Карта данных
Структура сущности
Граф JointJS
```

### Карта данных

Показывает карточки сущностей. В карточке выводятся первые поля, признак скрытых полей и краткий список связей сущности с другими сущностями. На карте есть фильтр по названию и ID сущности.

Клик по сущности открывает `Структура сущности`. Клик по связи в карточке сущности открывает `Структура сущности → Связи`.

### Структура сущности

Основной редактор. Слева список сущностей с фильтром, справа редактор сущности или поля.

Порядок вкладок:

```text
Поля
Связи
Требования
UI
API
Код
```

Удаление сущности или поля показывается только на вкладке `Поля` рядом с сохранением.

### Граф JointJS

Экспериментальное представление поверх JSON-схемы. Граф не является источником истины.

Правила графа:

- одинарный клик по сущности или связи выделяет объект и показывает свойства;
- двойной клик по сущности открывает редактор сущности;
- двойной клик по связи открывает вкладку `Связи`;
- координаты узлов и выбранный объект не сохраняются в логической схеме;
- если библиотека JointJS недоступна, модуль должен показать понятное сообщение, не ломая остальные вкладки.

## Связи с требованиями

Связи хранятся в:

```text
data_schema/mappings/requirement_data_links.json
```

Связь указывает на `requirements[].id`.

В UI связывание выполняется через фильтруемый список требований. В карточке требования показывать доступные признаки: группа, тип, статус, приоритет.

Источник требований задается файлом `requirements_source.json` и должен указывать на канонический JSON другого модуля внутри того же workspace.

## Связи с UI-схемой

Связи хранятся в:

```text
data_schema/mappings/ui_data_links.json
```

Основной способ выбора UI-объекта в интерфейсе — через API модуля `ui_schema`: выбор страницы, иерархия элементов, фильтр по типу элемента и текстовый фильтр.

Ручной ввод ID UI-элемента не является основным способом работы аналитика.

## Связи с API-схемой

Связи хранятся в:

```text
data_schema/mappings/api_data_links.json
```

API-схема как отдельный модуль пока не реализована. Текущий формат links уже предусматривает связь с API-ресурсом, операцией, DTO, параметром или другим API-объектом.

## Связи с кодом

Связи хранятся в:

```text
data_schema/code_links.json
```

В текущем UI связи с кодом только отображаются. Не добавлять ручное создание code links в UI без отдельного решения.

Наличие API для `code-links` не означает, что модуль генерирует код. Генерация кода не является задачей `data_schema`.

## Что не менять без отдельного решения

Не менять без явного требования:

```text
логический характер схемы данных;
отсутствие физического storage-мэппинга;
структуру <workspace>/data_schema/;
правило один файл на сущность;
формат field target_id как <entity_id>.<field_id>;
для вложенных ID допускается только техническая нормализация избыточно повторённого ID владельца; поиск по title, description или смыслу запрещён;
перечень поддерживаемых типов данных;
порядок вкладок редактора;
принцип, что index.json является производным файлом;
принцип, что JointJS-граф не хранит логическую модель;
отсутствие ручного добавления code links через UI.
```

## Встроенный агент синхронизации

Backend агента находится в `backend/modules/data_schema/agent_*.py`, внешние инструкции и промпты — в `modules/data_schema/agent/`, UI — в `frontend/modules/data_schema/js/agent-*.js`.

Основной workflow выполняет один ограниченный LangChain-agent. Он получает один компактный контекст, записывает структуру схемы, напрямую записывает результаты требований и завершает работу вызовом `validate_data_schema_state`. Отдельные generation plan, concept mappings и ролевые schema/traceability agents не используются.

После технической validation выполняются две независимые сфокусированные проверки: coverage требований и consistency схемы. Backend только объединяет их структурированные результаты. Первый correction-вызов получает сокращённый контекст затронутых требований и объектов и возвращает один полный структурированный план для всех `must_fix` и совместимых конкретных `advisory`. Backend применяет только явно перечисленные write, patch, remove и requirement-update операции как одну техническую транзакцию; при ошибке восстанавливает исходную корректную временную схему. Затем выполняется целевая verification. Если после неё остаются `must_fix`, следующие correction-раунды получают только эти blockers и выполняют минимальные точечные планы; после каждого плана запускается отдельная verification. Общее число correction-раундов ограничено `agent.semantic_review.max_correction_rounds`. Повторный полный audit запрещён. Backend не понижает severity и не выбирает исправления. Неустранённые настоящие `must_fix` блокируют apply; `advisory` отображаются как предупреждения. Кандидаты на ручную очистку возвращаются consistency review отдельным массивом, не включаются в issues, correction или recovery и не влияют на apply.

Нормальный порядок инструментов:

1. один `load_synchronization_context`;
2. при необходимости один пакетный `write_data_schema_dictionaries`;
3. при необходимости один пакетный `write_data_schema_core`;
4. при необходимости один пакетный `write_data_schema_relations`;
5. один полный `write_data_schema_traceability` со всеми входными requirement ID;
6. один `validate_data_schema_state`.

Полный набор итогов актуальных требований записывается одним вызовом. Каждый входной requirement ID должен присутствовать в нём ровно один раз. Отсутствие ранее известного ID не разрешает автоматическое удаление требования, его объектов или прежних связей. Backend сохраняет унаследованные links из базовой схемы, выводит их аналитику отдельно, а semantic review получает актуальный набор готовых требований. При технической ошибке backend выполняет не более одной отдельной попытки исправления с актуальным компактным контекстом. Перед финальной validation основной агент выполняет внутренний самоконтроль без отдельного tool call. Coverage review получает требования один раз, сгруппированными по уже записанному текущему результату, и сначала полностью проверяет `no_data`; такая группировка является только технической организацией контекста и не заменяет смысловую оценку LLM. Смысловые reviewers не должны требовать промышленную полноту или альтернативную более сложную модель: `must_fix` используется только для явного противоречия требованиям или непригодности прототипа, `advisory` — только для конкретного небольшого дефекта с однозначным минимальным исправлением.

Контекст основного агента должен содержать только:

- компактные требования с описанием, критериями приёмки и связями;
- редактируемые `schema`, `entities`, `relations`, `dictionaries`;
- точные канонические ID;
- допустимые логические типы и cardinality;
- ошибки текущей технической проверки.

Не включать в основной контекст UI/API/code links, полные requirement links предыдущего результата, generation plan, concept mappings и другие промежуточные документы. Полные документы допускаются только в диагностике и специализированных read-only helper-функциях.

Backend агента выполняет только технические операции: разбирает JSON-аргументы, проверяет обязательные поля и enum, проверяет точное существование ID, сохраняет файлы, строит индекс, проверяет сохранность базовых объектов и формирует diff. Backend не выбирает сущность, поле, отношение, справочник, classification или link relation за модель; не применяет fuzzy/alias matching и не исправляет содержательные ответы LLM.

Существующие объекты изменять по точным ID. Для частичного изменения использовать patch-операции, для новых объектов — write-операции. Удалять разрешено только объекты, добавленные текущим запуском. Основной агент выполняет инструменты последовательно. Семантическая коррекция не использует последовательный tool-loop: LLM возвращает единый самодостаточный план, а backend применяет его операции в фиксированном техническом порядке без содержательного анализа.

Промпты должны быть универсальными и не содержать демонстрационных сущностей, значений или схем. Они должны различать `defines`, `uses`, `validates`, `clarifies`, проверять реальную зависимость требования от данных и не создавать формальные или косвенно дублирующиеся ссылки. `no_data` допустимо только для требований без использования предметных данных; отображение, ввод, выбор, изменение, фильтрация или агрегация существующих данных получают прямую трассировку. Конкретные значения справочников допускаются только при прямом перечислении. Справочник требуется для явно заданного именованного перечня, когда элементу достаточно `id`, `title`, `description`; при дополнительных характеристиках используется сущность.

Все изменяемые лимиты, провайдеры, URL, сетевые retry, профили reasoning по провайдеру и точечные переопределения профиля для модели, пути к prompt/reference-файлам и другие параметры агента хранятся в `modules/data_schema/config.yaml`. Внутренние retry провайдера должны оставаться отключёнными; допускаются только явно настроенные и учитываемые повторы временных HTTP-ошибок. Таймауты не повторять автоматически. Текст prompt и инструкций хранится только в отдельных Markdown-файлах. Не помещать prompt-текст и изменяемые параметры в Python или JavaScript.

Крупные Python и JavaScript файлы декомпозировать по ответственности. Отдельно держать orchestration запуска, построение контекста, модели tool payload, запись схемы, validation, observability и работу с run storage.

Каждый запуск хранится в `<workspace>/.protoarchitect/data_schema_agent/runs/<run_id>/` и формирует события, метрики LLM/tool calls/токенов, техническую validation, структурный diff, итоговый отчёт и диагностический ZIP без секретов. После применения, отклонения или отмены тяжёлые runtime-файлы удаляются, остаются компактный `run.json` и `diagnostics/attempt_<n>.zip`.

Рабочая схема блокируется от ручной записи, пока запуск имеет статус `running`, `cancelling`, `preview_ready`, `applying` или `failed`. Изменения применяются атомарно после подтверждения человеком. Перед применением внешний файл требований повторно проверяется по SHA-256.

## Правила для LLM-агента

При доработке модуля:

1. Определить, меняется ли структура хранения, API, backend-логика, frontend UI или документация.
2. Если меняется структура JSON-файлов, обновить `modules/data_schema/docs/STORAGE.md`.
3. Если меняется API, обновить `backend/modules/data_schema/API.md` и `modules/data_schema/api.openapi.yaml`.
4. Если меняются связи с другими модулями, обновить `modules/data_schema/interop.yaml`.
5. Если меняется назначение, возможности или структура интерфейса, обновить `README.md`.
6. Если меняются правила доработки или архитектура модуля, обновить `AGENTS.md`.
7. Не добавлять физические особенности хранения в схему данных.
8. Не добавлять демо-данные в `modules/data_schema/init/`.
9. Не редактировать `index.json` вручную.
10. Не создавать большие JS/Python-файлы; декомпозировать по ответственности.
11. Не использовать ручной ввод ID как основной пользовательский сценарий создания объектов.
12. Сохранять схему понятной аналитику и пригодной для обработки LLM.
