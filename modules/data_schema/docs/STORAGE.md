# Структура хранения модуля `data_schema`

Документ описывает файлы хранения логической схемы данных прототипа. Он не описывает работу интерфейса модуля, алгоритмы backend и физическую реализацию хранения данных в создаваемом прототипе.

## Назначение схемы

Схема данных описывает логические данные предметной области:

- сущности;
- поля сущностей;
- логические типы полей;
- справочники;
- логические связи между сущностями;
- связи объектов схемы данных с требованиями;
- связи объектов схемы данных с UI-схемой;
- связи объектов схемы данных с API-схемой или будущим описанием API;
- предусмотренные связи объектов схемы данных с файлами кода.

Схема не описывает SQL-таблицы, колонки, SQL-типы, индексы, миграции, ORM-маппинги, транзакции, права доступа и бизнес-поведение.

## Корневая папка данных

Для каждого workspace данные модуля находятся в папке:

```text
<workspace>/data_schema/
```

## Иерархия файлов

```text
data_schema/
  schema.json
  index.json
  entities/
    <entity_id>.json
  relations.json
  dictionaries.json
  mappings/
    requirement_data_links.json
    ui_data_links.json
    api_data_links.json
  code_links.json
  requirements.json
```

Файл `requirements.json` может использоваться как локальный источник требований для демонстрации и трассировки. Структура `requirements.json` в этом документе не описывается. Ссылки из схемы данных идут на поле `requirements[].id`.

## Источник истины

Основные файлы схемы:

```text
schema.json
entities/<entity_id>.json
relations.json
dictionaries.json
mappings/requirement_data_links.json
mappings/ui_data_links.json
mappings/api_data_links.json
code_links.json
```

Файл `index.json` пересобирается из основных файлов и не является источником истины.

## Правила формирования идентификаторов

Идентификаторы создаваемых сущностей, полей и связей формируются автоматически при создании объекта.

Правила формирования:

1. Исходное значение берется из названия объекта.
2. Русские буквы транслитерируются в латиницу.
3. Значение приводится к нижнему регистру.
4. Пробелы и недопустимые символы заменяются на `_`.
5. Повторяющиеся `_` заменяются на один `_`.
6. Символ `_` в начале и конце удаляется.
7. Допустимы только символы `a-z`, `0-9`, `_`.
8. Если результат пустой, используется fallback-значение типа объекта: `entity`, `field`, `relation` или `item`.
9. Если идентификатор начинается с цифры, добавляется fallback-префикс.
10. Если идентификатор уже занят в соответствующей области, добавляется числовой суффикс `_2`, `_3` и далее.

Примеры:

| Тип объекта | Название | Идентификатор |
| --- | --- | --- |
| entity | `Счет` | `schet` |
| entity | `Заявка на кредит` | `zayavka_na_kredit` |
| field | `Номер счета` | `nomer_scheta` |
| relation | `Счета клиента` | `scheta_klienta` |
| entity | `123 Архив` | `entity_123_arhiv` |

Области уникальности:

| Объект | Где должен быть уникален идентификатор |
| --- | --- |
| сущность | среди `schema.entities[].id` |
| поле | внутри массива `fields` одной сущности |
| связь сущностей | среди `relations[].id` |
| справочник | среди `dictionaries[].id` |
| значение справочника | внутри `values` одного справочника |
| ссылка | среди ссылок соответствующего файла `links` |

LLM при создании новых объектов должна передавать содержательное название. Сгенерированный идентификатор нужно брать из ответа API или из обновленного файла схемы. Не нужно заранее придумывать `id`, если объект создается через API.

## Форматы ссылок на объекты

| Объект | Формат ссылки |
| --- | --- |
| сущность | `<entity_id>` |
| поле | `<entity_id>.<field_id>` |
| связь сущностей | `<relation_id>` |
| справочник | `<dictionary_id>` |
| значение справочника | `<dictionary_id>.<value_id>` |
| требование | значение поля `requirements[].id` |
| UI-объект | идентификатор объекта из `ui_schema` |
| API-объект | идентификатор объекта из API-схемы или будущего описания API |
| файл кода | относительный путь от корня workspace или от корня генерируемого прототипа |

Допустимые значения `target_type` и `data_target_type`:

```text
entity
field
relation
dictionary
dictionary_value
```

## Поддерживаемые типы данных полей

Тип поля является логическим типом. Он не является SQL-типом и не задает физический способ хранения.

| Тип | Описание | Пример поля |
| --- | --- | --- |
| `string` | Короткое текстовое значение. | номер счета, email, телефон |
| `text` | Длинное текстовое значение. | комментарий, описание |
| `integer` | Целое число. | срок в месяцах, количество попыток |
| `decimal` | Число с дробной частью. | сумма, баланс, процентная ставка |
| `boolean` | Логическое значение да/нет. | признак согласия, флаг активности |
| `date` | Календарная дата без времени. | дата исполнения, дата рождения |
| `datetime` | Дата и время. | время операции, дата создания записи |
| `uuid` | Универсальный логический идентификатор. | идентификатор сущности, ссылка на объект |
| `dictionary` | Значение из справочника `dictionaries.json`. | статус, валюта, тип кредита |
| `json` | Вложенное структурированное значение. | дополнительные параметры, внешний payload |

Для поля типа `dictionary` указывается `dictionary_id`. Для остальных типов поле `dictionary_id` не используется.

## `schema.json`

Файл содержит общее описание схемы и реестр сущностей.

Создается один файл на схему данных workspace:

```text
data_schema/schema.json
```

Пример:

```json
{
  "schema_version": "0.1",
  "title": "Логическая схема данных банковского фронт-офиса",
  "description": "Схема данных для прототипа банковского фронт-офиса.",
  "entities": [
    {
      "id": "customer",
      "title": "Клиент",
      "file": "entities/customer.json"
    },
    {
      "id": "account",
      "title": "Счет",
      "file": "entities/account.json"
    }
  ]
}
```

Поля файла:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `schema_version` | string | да | Версия формата схемы данных. Текущее значение: `0.1`. |
| `title` | string | да | Название схемы данных. |
| `description` | string | нет | Описание схемы данных. |
| `entities` | array | да | Реестр сущностей схемы. |

Элемент массива `entities`:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `id` | string | да | Идентификатор сущности. |
| `title` | string | да | Человекочитаемое название сущности. |
| `file` | string | да | Относительный путь к файлу сущности. |

Новый элемент массива `entities` создается при создании новой сущности. При удалении сущности соответствующий элемент удаляется из массива `entities`.

## `entities/<entity_id>.json`

Файл описывает одну логическую сущность.

Для каждой сущности создается отдельный файл:

```text
data_schema/entities/<entity_id>.json
```

Правило имени файла:

```text
<entity_id>.json
```

Примеры имен файлов:

```text
entities/customer.json
entities/account.json
entities/deposit_application.json
```

Пример содержимого:

```json
{
  "id": "account",
  "title": "Счет",
  "description": "Банковский счет клиента.",
  "fields": [
    {
      "id": "id",
      "title": "Идентификатор счета",
      "type": "uuid",
      "required": true,
      "description": "Уникальный идентификатор счета."
    },
    {
      "id": "number",
      "title": "Номер счета",
      "type": "string",
      "required": true,
      "description": "Номер счета, отображаемый пользователю."
    },
    {
      "id": "currency",
      "title": "Валюта",
      "type": "dictionary",
      "required": true,
      "description": "Валюта счета.",
      "dictionary_id": "currency"
    }
  ]
}
```

Поля файла сущности:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `id` | string | да | Идентификатор сущности. Совпадает с именем файла без `.json`. |
| `title` | string | да | Название сущности. |
| `description` | string | нет | Описание сущности. |
| `fields` | array | да | Список полей сущности. |

Элемент массива `fields`:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `id` | string | да | Идентификатор поля внутри сущности. |
| `title` | string | да | Название поля. |
| `type` | string | да | Логический тип поля из поддерживаемого перечня. |
| `required` | boolean | да | Логическая обязательность поля. |
| `description` | string | нет | Описание поля. |
| `dictionary_id` | string | только для `dictionary` | Идентификатор справочника из `dictionaries.json`. |

Новый элемент массива `fields` создается при добавлении нового поля в сущность. Ссылка на поле во внешних файлах использует формат `<entity_id>.<field_id>`.

## `relations.json`

Файл содержит логические связи между сущностями.

Создается один файл на схему данных workspace:

```text
data_schema/relations.json
```

Пример:

```json
{
  "relations": [
    {
      "id": "customer_accounts",
      "title": "Счета клиента",
      "source_entity": "customer",
      "target_entity": "account",
      "cardinality": "one_to_many",
      "description": "Один клиент может иметь несколько счетов."
    }
  ]
}
```

Поля файла:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `relations` | array | да | Список логических связей между сущностями. |

Элемент массива `relations`:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `id` | string | да | Идентификатор связи. |
| `title` | string | да | Название связи. |
| `source_entity` | string | да | Идентификатор исходной сущности. |
| `target_entity` | string | да | Идентификатор целевой сущности. |
| `cardinality` | string | да | Кардинальность связи. |
| `description` | string | нет | Описание связи. |

Поддерживаемые значения `cardinality`:

| Значение | Описание |
| --- | --- |
| `one_to_one` | Один объект исходной сущности связан с одним объектом целевой сущности. |
| `one_to_many` | Один объект исходной сущности связан со многими объектами целевой сущности. |
| `many_to_one` | Многие объекты исходной сущности связаны с одним объектом целевой сущности. |
| `many_to_many` | Многие объекты исходной сущности связаны со многими объектами целевой сущности. |

Новый элемент массива `relations` создается при добавлении связи между сущностями.

## `dictionaries.json`

Файл содержит логические справочники и ограниченные списки значений.

Создается один файл на схему данных workspace:

```text
data_schema/dictionaries.json
```

Пример:

```json
{
  "dictionaries": [
    {
      "id": "currency",
      "title": "Валюта",
      "values": [
        {
          "id": "RUB",
          "title": "Российский рубль"
        },
        {
          "id": "USD",
          "title": "Доллар США"
        }
      ]
    }
  ]
}
```

Поля файла:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `dictionaries` | array | да | Список справочников. |

Элемент массива `dictionaries`:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `id` | string | да | Идентификатор справочника. |
| `title` | string | да | Название справочника. |
| `values` | array | да | Значения справочника. |

Элемент массива `values`:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `id` | string | да | Идентификатор значения внутри справочника. |
| `title` | string | да | Название значения. |

Новый элемент массива `dictionaries` создается при добавлении нового справочника. Новый элемент массива `values` создается при добавлении значения в справочник.

## `mappings/requirement_data_links.json`

Файл содержит связи требований с объектами схемы данных.

Создается один файл на схему данных workspace:

```text
data_schema/mappings/requirement_data_links.json
```

Пример:

```json
{
  "links": [
    {
      "id": "req_account_balance",
      "requirement_id": "REQ-ACCOUNTS-LIST",
      "target_type": "field",
      "target_id": "account.balance",
      "relation": "defines",
      "implementation_status": "planned"
    }
  ]
}
```

Поля файла:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `links` | array | да | Список связей требований с объектами схемы данных. |

Элемент массива `links`:

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `id` | string | да | Идентификатор связи. |
| `requirement_id` | string | да | Идентификатор требования. Ссылается на `requirements[].id`. |
| `target_type` | string | да | Тип объекта схемы данных. |
| `target_id` | string | да | Идентификатор объекта схемы данных. |
| `relation` | string | да | Тип смысловой связи. |
| `implementation_status` | string | да | Статус реализации или проверки связи. |

Новый элемент массива `links` создается при связывании требования с сущностью, полем, связью сущностей, справочником или значением справочника.

Рекомендуемые значения `relation`:

```text
defines
clarifies
validates
```

Рекомендуемые значения `implementation_status`:

```text
planned
implemented
needs_review
```

| `path` | string | да | Относительный путь к файлу кода. |
| `status` | string | да | Статус связи с кодом. |

Новый элемент массива `links` создается при связывании объекта схемы данных с файлом кода. В текущем UI такие ссылки отображаются, но вручную не добавляются.

Рекомендуемые значения `code_type`:

```text
model
schema
repository
service
api
migration
seed
```

Рекомендуемые значения `status`:

```text
planned
generated
manual
outdated
```

## `index.json`

Файл содержит компактный индекс схемы для UI и LLM.

Создается один файл на схему данных workspace:

```text
data_schema/index.json
```

Пример:

```json
{
  "schema": {
    "schema_version": "0.1",
    "title": "Логическая схема данных банковского фронт-офиса",
    "description": "Схема данных для прототипа.",
    "entities": [
      {
        "id": "account",
        "title": "Счет",
        "file": "entities/account.json"
      }
    ]
  },
  "entities": [
    {
      "id": "account",
      "title": "Счет",
      "description": "Банковский счет клиента.",
      "field_count": 2,
      "fields": [
        {
          "id": "id",
          "title": "Идентификатор счета",
          "type": "uuid",
          "required": true
        },
        {
          "id": "number",
          "title": "Номер счета",
          "type": "string",
          "required": true
        }
      ]
    }
  ],
  "relations": [],
  "dictionaries": []
}
```

Поля файла:

| Поле | Тип | Описание |
| --- | --- | --- |
| `schema` | object | Копия общего описания схемы из `schema.json`. |
| `entities` | array | Компактное описание сущностей и их полей. |
| `relations` | array | Копия массива `relations` из `relations.json`. |
| `dictionaries` | array | Копия массива `dictionaries` из `dictionaries.json`. |

Элемент массива `entities` в `index.json`:

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | string | Идентификатор сущности. |
| `title` | string | Название сущности. |
| `description` | string | Описание сущности. |
| `field_count` | integer | Количество полей сущности. |
| `fields` | array | Компактный список полей. |

Элемент массива `fields` в `index.json`:

| Поле | Тип | Описание |
| --- | --- | --- |
| `id` | string | Идентификатор поля. |
| `title` | string | Название поля. |
| `type` | string | Логический тип поля. |
| `required` | boolean | Признак обязательности поля. |

`index.json` обновляется после изменений структуры схемы. Не редактировать `index.json` вручную.

## `requirements.json`

Файл может использоваться как локальный источник требований для демонстрации и трассировки.

Структура файла требований в этом документе не описывается.

Ссылки из `mappings/requirement_data_links.json` идут на поле:

```text
requirements[].id
```

Модуль `data_schema` не должен редактировать требования как бизнес-данные.

## Init-шаблон

Пустая структура для нового workspace хранится в:

```text
modules/data_schema/init/
```

Init-шаблон должен содержать только минимальный набор файлов без демонстрационных сущностей, полей, связей и требований:

```text
schema.json
index.json
relations.json
dictionaries.json
mappings/requirement_data_links.json
mappings/ui_data_links.json
mappings/api_data_links.json
code_links.json
requirements.json
```

Демо-данные должны храниться в конкретном workspace, например:

```text
data/workspaces/ws_demo/data_schema/
```

## Ограничения текущей версии

- схема описывает только логический уровень данных;
- схема не описывает SQL-таблицы, SQL-колонки и SQL-типы;
- схема не описывает индексы, ключи, миграции и ORM-маппинги;
- схема не описывает настройки PostgreSQL, MySQL или JSON-хранилища;
- схема не описывает бизнес-поведение прототипа;
- связи с UI-схемой хранятся как ссылки на объекты `ui_schema`;
- API-схема как отдельный модуль пока не реализована;
- связи с кодом предусмотрены и отображаются, но не являются механизмом генерации кода;
- `requirements.json` является локальным источником требований только до появления отдельного модуля требований;
- `index.json` является производным файлом и не редактируется вручную.
