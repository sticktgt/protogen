# Data Schema

`data_schema` — модуль работы с логической схемой данных прототипа.

Модуль описывает данные предметной области на уровне сущностей, полей, логических связей и трассировки к требованиям, UI, API и коду. Схема предназначена для ручной работы аналитика, использования LLM при развитии требований и дальнейшей генерации прототипа.

Модуль не описывает физическое хранение данных: SQL-таблицы, колонки, индексы, миграции, ORM-маппинги, настройки PostgreSQL/MySQL/JSON-хранилища, транзакции и бизнес-поведение остаются в требованиях и в создаваемом коде прототипа.

## Основные возможности

- ведение списка логических сущностей;
- ведение полей сущностей с ограниченным набором логических типов данных;
- автоматическое формирование идентификаторов сущностей, полей и связей;
- описание логических связей между сущностями;
- связь сущностей, полей, связей и справочников с требованиями;
- связь объектов схемы данных с элементами UI-схемы;
- связь объектов схемы данных с будущей API-схемой;
- отображение предусмотренных связей с кодом;
- компактный индекс схемы для UI и LLM;
- пустой init-шаблон для новых workspace и отдельные демо-данные в demo workspace.

## Интерфейс

Модуль содержит четыре основных представления.

### Карта данных

Карточное представление сущностей. В карточке сущности показываются название, идентификатор, несколько первых полей, признак скрытых полей и краткий список связей с другими сущностями. На карте есть фильтр по названию и идентификатору сущности.

### Структура сущности

Основной редактор схемы. Слева отображается список сущностей с фильтром. Справа открывается редактор выбранной сущности или поля.

Для сущности и поля используются вкладки:

```text
Поля
Связи
Требования
UI
API
Код
```

На вкладке `Поля` редактируются свойства сущности или поля. Удаление сущности или поля доступно только на этой вкладке рядом с сохранением.

На вкладке `Связи` редактируются логические связи между сущностями. Связи можно создавать, изменять и удалять.

На вкладке `Требования` создаются и удаляются связи с требованиями. Требование выбирается через фильтруемый список с отображением группы, типа, статуса и приоритета, если эти признаки есть в источнике требований.

На вкладке `UI` создаются и удаляются связи с UI-схемой. UI-элемент выбирается через API модуля `ui_schema`: страница, иерархия элементов, фильтр по типу и текстовый фильтр.

На вкладке `API` создаются и удаляются связи с API-схемой или будущим описанием API.

На вкладке `Код` отображаются предусмотренные связи с файлами кода. Ручное добавление кодовых ссылок через UI не используется.

### AI-синхронизация

Агент синхронизирует логическую схему с выбранным внешним файлом требований другого модуля. Файл может содержать полный набор либо только текущую изменённую часть. Запуск выполняется во временной копии схемы через ограниченный LangChain tool-calling agent без shell и произвольного доступа к workspace.

Основной агент работает одним последовательным циклом:

1. загружает компактный контекст требований и текущей схемы;
2. записывает справочники, сущности с полями и отношения;
3. напрямую записывает итог каждого требования: точные ссылки на объекты схемы либо одну из классификаций `cross_cutting_data`, `no_data`, `unclear`;
4. запускает техническую проверку результата.

После технической проверки выполняются две независимые сфокусированные проверки: покрытие требований и внутренняя согласованность схемы. Их результаты объединяются технически без содержательного анализа в backend. Если найдены конкретные замечания, LLM получает только связанные требования и объекты и одним структурированным ответом формирует полный план минимальных исправлений для `must_fix` и совместимых `advisory`. Backend применяет перечисленные операции как одну техническую транзакцию и откатывает их целиком при ошибке. Затем reviewer проверяет только исходные замечания и непосредственные регрессии. Повторный полный аудит не запускается. Неустранённые `must_fix` блокируют применение; оставшиеся `advisory` показываются как предупреждения.

Отдельные generation plan, concept mappings и пакетная генерация трассировки не используются. Основной агент записывает полную трассировку актуального набора требований, готовых на момент запуска, одним вызовом. Связи требований, уже существовавшие в базовой схеме и отсутствующие в актуальном наборе, сохраняются без изменений и выводятся аналитику отдельным списком. Consistency review может дополнительно сформировать кандидаты на ручную очистку схемы. Эти списки не участвуют в correction/recovery, не вызывают автоматических удалений и не влияют на возможность применения. Backend не анализирует смысл требований, не выбирает сущности и связи и не исправляет содержательные решения модели. Он проверяет JSON-контракты, допустимые типы, точное существование ID, сохранность базовых объектов, полноту итоговой классификации актуального набора и наличие завершённого смыслового approval перед применением.

Контекст агента содержит только поля требований, необходимые для проектирования, редактируемую логическую схему и каталог точных ID. UI/API/code links и промежуточные документы других этапов в основной prompt не включаются. Это уменьшает число токенов и рассчитано на использование небольших моделей.

Новые значения справочников создаются только при прямом перечислении в требованиях. Справочник используется для явно заданного именованного перечня или перечисленных значений, когда элементу достаточно `id`, `title`, `description`. Если элемент имеет другие собственные характеристики или связи, используется сущность. Простое упоминание допустимых значений без состава перечня не заставляет заменять естественный логический тип поля справочником. UI-требование, которое читает, показывает, вводит или фильтрует предметные данные, получает прямую трассировку к существующим объектам и не считается `no_data` только потому, что не создаёт новую структуру.

Защитные лимиты вызовов, токенов, длительности, сетевого запроса и смыслового контроля задаются в `modules/data_schema/config.yaml`. Уровень reasoning задаётся по провайдеру и при необходимости переопределяется для конкретной модели и роли вызова: generation, correction, review или проверка соединения. Скрытые повторы провайдера отключены. Для быстро возвращённых временных серверных HTTP-ошибок разрешён один явно учитываемый повтор; таймауты не повторяются, поэтому один зависший запрос по-прежнему ограничен `request_timeout_seconds`. Нормальный запуск содержит прямую генерацию, одну техническую validation и две сфокусированные смысловые проверки. Coverage review получает все требования один раз, сгруппированными по текущему результату агента, и в первую очередь полностью перепроверяет `no_data`. Первый semantic correction исправляет все blockers и совместимые конкретные рекомендации одним структурированным планом. Если verification оставляет настоящие blockers, допускаются ограниченные точечные recovery-раунды только для них; каждый раунд состоит из одного структурированного correction-вызова и одной целевой verification. Количество всех correction-раундов задаётся `agent.semantic_review.max_correction_rounds`. Backend применяет только явно переданные операции и не выбирает смысловые исправления. Применить можно результат без неустранённых `must_fix`; локальные недостатки прототипа остаются `advisory` и не блокируют применение. Любой результат можно открыть как read-only preview, отклонить или перегенерировать с комментарием.

В интерфейсе показываются этап выполнения, статистика времени, вызовов LLM и инструментов, расход токенов, журнал событий, структурный diff, предупреждения агента и отдельная информация для ручной проверки: унаследованные links отсутствующих требований и кандидаты на очистку схемы. Все файлы запуска находятся в `.protoarchitect/data_schema_agent/runs/<run_id>/`. После применения, отклонения или отмены тяжёлые рабочие данные удаляются; остаются компактный `run.json` и `diagnostics/attempt_<n>.zip` без API-ключей.

### Граф JointJS

Экспериментальное графическое представление сущностей и связей. Источник истины остается в JSON-файлах модуля.

В графе показываются сущности, первые поля сущности с иконками типов данных и логические связи между сущностями. Одинарный клик выделяет сущность или связь и показывает краткие свойства. Двойной клик по сущности открывает редактор сущности, двойной клик по связи открывает вкладку `Связи`.

Координаты узлов и состояние выделения не сохраняются в логической схеме данных.

## Хранение данных

Рабочие данные модуля находятся в папке workspace:

```text
<workspace>/data_schema/
```

Структура файлов, правила именования, поддерживаемые типы данных и форматы ссылок описаны в документе:

```text
modules/data_schema/docs/STORAGE.md
```

Файлы начальной пустой структуры для нового workspace находятся в:

```text
modules/data_schema/init/
```

Демо-данные не должны храниться в `init/`. Демо-схема может находиться только в конкретном workspace, например:

```text
data/workspaces/ws_demo/data_schema/
```

## API

Backend API модуля доступен с префиксом:

```text
/api/data-schema
```

Человекочитаемое описание API находится в:

```text
backend/modules/data_schema/API.md
```

Машинно-читаемое описание находится в:

```text
modules/data_schema/api.openapi.yaml
```

## Документы

```text
modules/data_schema/README.md              — краткое описание модуля
modules/data_schema/docs/STORAGE.md        — структура хранения данных
backend/modules/data_schema/API.md         — описание API для человека и LLM
modules/data_schema/AGENTS.md              — инструкция для LLM-агента или Codex
modules/data_schema/api.openapi.yaml       — OpenAPI-описание API
modules/data_schema/interop.yaml           — точки сопряжения с другими модулями
```

Документы обновляются только при изменении поведения, API, структуры хранения или правил доработки, которые затрагивают их содержание.

## Ограничения текущей версии

- схема не описывает физическую реализацию хранения данных;
- схема не описывает SQL, миграции, индексы и ORM;
- схема не описывает бизнес-поведение прототипа;
- API-схема как отдельный модуль пока не реализована;
- требования принадлежат внешнему модулю и подключаются через workspace-relative ссылку в `requirements_source.json`;
- граф JointJS является экспериментальным представлением и не хранит собственную модель данных;
- связи с кодом предусмотрены и отображаются, но не являются механизмом генерации кода.
