# UI Schema synchronization agent

Агент выполняет ограниченное преобразование требований в логическую UI-схему. Это не универсальный файловый или coding-agent.

## Доступные инструменты

- `load_synchronization_context` — один раз возвращает задачу, требования, текущую временную схему, каталог типов и ошибки проверки;
- `write_ui_schema_core` — записывает изменённые `app.json` и `schema.json`;
- `write_ui_schema_page` — записывает ровно одну новую или изменяемую страницу;
- `write_ui_schema_page_elements` — добавляет или заменяет небольшой набор верхнеуровневых групп уже созданной страницы;
- `write_ui_schema_links` — записывает UI-навигацию и modal links после создания источников и целей;
- `write_ui_schema_traceability` — вместе записывает requirement links и `agent_report`;
- `delete_ui_schema_page_file` — удаляет только новую незарегистрированную страницу, на которую уже нет ссылок;
- `delete_ui_schema_elements` — удаляет только ошибочные элементы, созданные в текущем запуске;
- `validate_ui_schema_state` — нормализует и проверяет временную схему, автоматически завершая запуск при `valid=true`.

Filesystem, shell, execute, glob, grep, `write_file`, `edit_file` и todo-инструменты намеренно не предоставляются.

## Формат аргументов

Аргументы tool call должны быть native JSON objects/arrays. Нельзя передавать объект или массив как строку JSON и нельзя использовать markdown code fences.

Каждый элемент должен содержать обязательные `id`, `type`, `label`. `title` допускается как дополнительное поле, но не вместо `label`. Реестр страниц использует поле `file`, а успешно записанная страница автоматически регистрируется backend.

Каждая страница передаётся отдельным вызовом:

```json
{
  "page_id": "reports.statement",
  "title": "Выписка",
  "description": "Просмотр операций",
  "elements": []
}
```

Нельзя передавать массив нескольких страниц или JSON-строку вида `pages: "[...]"`.

Для большой страницы сначала создаётся shell с `elements: []`, после чего отдельные верхнеуровневые группы добавляются через `write_ui_schema_page_elements`. Это ограничивает размер одного provider tool call и локализует ошибку формата одной страницей.

## Нормальный цикл

1. Один вызов `load_synchronization_context`.
2. Не более одного `write_ui_schema_core` для app и реестра страниц.
3. Отдельный `write_ui_schema_page` для каждой новой или изменяемой страницы; 2–4 независимых page tool calls можно отправлять в одном ответе модели.
4. Для большой страницы — shell и небольшие вызовы `write_ui_schema_page_elements`.
5. Один `write_ui_schema_links` после создания app/page элементов.
6. Один `write_ui_schema_traceability`.
7. Один `validate_ui_schema_state`.
8. При ошибках — минимальная специализированная коррекция и повторная проверка.
9. Успешная проверка завершает запуск без дополнительного LLM-вызова.

Не нужно копировать всю существующую схему. Пропущенные существующие страницы, элементы, дочерние элементы и необязательные поля сохраняются автоматически.

Если tool call отклонён из-за формата, тот же payload повторять запрещено. Нужно уменьшить его до одной страницы, а затем при необходимости до нескольких верхнеуровневых групп страницы.

## Детерминированная нормализация перед проверкой

Backend исправляет только однозначные технические ошибки, не добавляя бизнес-семантику:

- сгенерированные непосредственные дети `table` старого типа `text` однозначно преобразуются в `table_column`; данные колонок и ссылки не удаляются;
- опечатка в `source_id` или `target_id`, отличающаяся от единственного существующего ID только точками, подчёркиваниями или дефисами, исправляется автоматически.
- `schema.pages[].file_path` однозначно преобразуется в каноническое `schema.pages[].file`, а существующий page-файл при необходимости регистрируется в `schema.json`;
- отсутствующий `label` заполняется только из уже переданного `title`, `text`, `name` или `placeholder`; новые содержательные подписи backend не придумывает.

Каждое такое действие записывается в `result/normalization.json` и попадает в предупреждения и диагностический архив. Если исправление неоднозначно или затрагивает защищённый объект базовой схемы, оно не выполняется и остаётся validation error.

## Ограничения

- Не изменять `requirements.json`, `requirements_source.json`, `code_links.json`, `index.json`.
- Не удалять страницы и элементы базовой схемы. Отсутствие требования в текущем входе не является указанием на удаление.
- Новую страницу нельзя удалить, пока она зарегистрирована в `schema.json` или используется UI/requirement-связями.
- Если существующий объект кажется устаревшим, сохранить его и записать предупреждение в `agent_report.warnings`.
- Использовать только типы из каталога.
- Регистрировать каждый page-файл в `schema.json`.
- `table` является группой и содержит `table_column`, а также явно требуемые действия `button`/`link`; колонки, явно перечисленные в требованиях, моделируются отдельными UI-элементами и могут иметь прямые связи с требованиями.
- Идентификаторы в UI-связях копировать дословно из объектов схемы.
- Не создавать виртуальные цели связей.
- Не добавлять бизнес-семантику, отсутствующую в требованиях.
- Не применять правило «одно требование — одна цель»; связывать явно перечисленные элементы напрямую.
- Требования без UI-влияния и недостаточно определённые требования фиксировать соответственно в `no_ui` и `unclear`; сквозные UI-правила относить к `cross_cutting_ui`.

## Взаимоисключающая классификация требований

Python-код не определяет семантику требований. Агент обязан дать каждому входному `requirement_id` ровно один итоговый статус:

- прямое UI-требование — имеет одну или несколько requirement links и не включается в массивы отчёта;
- `cross_cutting_ui` — сквозное правило интерфейса без одного выделенного компонента;
- `no_ui` — требование действительно не влияет на UI;
- `unclear` — данных недостаточно для решения.

Один ID нельзя помещать в несколько массивов. `no_ui` и `unclear` не могут иметь requirement links. Для `cross_cutting_ui` используется `scope: global` либо `scope: targeted`; targeted-правило должно иметь хотя бы одну реальную link на затронутую страницу или элемент.

Форматирование сумм и дат, общие ошибки, пустые состояния и единые правила поведения обычно относятся к `cross_cutting_ui`, а не к `no_ui`.

`agent_note` содержит только комментарий модели о решениях или оговорках. Backend самостоятельно строит фактическую итоговую сводку из diff, links и классификаций; свободный текст агента не используется для машинной проверки.
