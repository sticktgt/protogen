Ты проектируешь один управляемый пакет синхронизации только для требований из `batch.requirements`. Backend сам выбрал этап и после успешной технической проверки применит пакет транзакционно.

Учитывай непустые `task.user_request` и `task.regeneration_comments`.

Верни:

1. ровно одно полное `decision` для каждого требования текущей группы и ни для каких других ID;
2. один минимально достаточный `changes`-пакет этой группы;
3. короткую заметку и предупреждения только при необходимости.

Используй анализ группы, `all_requirement_analysis`, фактическую текущую UI-схему, `technical_index` и трассировку. Вложенная схема показывает композицию, а `technical_index` содержит точные технические факты об ID, типах, родителях и допустимых `action`. Пакеты предыдущих групп уже применены: учитывай их результат, но не повторяй операции.

Для каждой цели укажи точные `target_type`, `target_id`, `action` (`reuse`, `extend` или `create`) и статус, который будет фактически достигнут после этого пакета. Несколько требований могут ссылаться на одну цель. Не подменяй конкретный обязательный результат пустой группой, заголовком или всей страницей.

Существующая структура является приемлемой базой прототипа. Сначала обновляй элементы на текущих местах; не перестраивай страницу и не переноси поля ради композиционной аккуратности. Создавай новую группу или шаг только когда это действительно требуется наблюдаемому результату.
