Выполни одну полную синхронизацию UI-схемы.

Используй только native JSON в аргументах инструментов. Не передавай JSON как строку и не используй markdown code fences.

Порядок:

1. `load_synchronization_context` — один раз.
2. `write_ui_schema_core` — только изменённые `app` и `schema_document`, максимум один вызов.
3. `write_ui_schema_page` — отдельный вызов для каждой новой или изменяемой страницы. Можно отправлять 2–4 независимых page tool calls в одном ответе модели.
4. Для большой страницы: сначала `write_ui_schema_page` с `elements: []`, затем `write_ui_schema_page_elements` небольшими пакетами верхнеуровневых групп.
5. `write_ui_schema_links` — UI-навигация и modal links после создания страниц и элементов, один вызов.
6. `write_ui_schema_traceability` — requirement links и взаимоисключающая классификация всех требований, один вызов.
7. `validate_ui_schema_state`.
8. При ошибках исправь только затронутую часть соответствующим специализированным инструментом и повтори проверку.

Не передавай массив нескольких страниц как строку. Не повторяй отклонённый payload. Пропущенные существующие страницы, элементы и поля сохраняются backend автоматически. `table` содержит дочерние `table_column` и только явно требуемые действия `button`/`link`; для явно перечисленных колонок создай реальные элементы и прямые связи требований. Идентификаторы в связях копируются дословно из схемы.

Классификация обязательна для каждого requirement ID: прямые UI-требования имеют links и не входят в массивы отчёта; остальные ровно один раз относятся к `cross_cutting_ui`, `no_ui` или `unclear`. Форматы, общие ошибки, пустые состояния и единые правила поведения обычно относятся к `cross_cutting_ui`, а не к `no_ui`.
Каждый элемент в `elements`/`children` передавай как объект с обязательными `id`, `type`, `label`; не полагайся только на `title`. В `schema_document.pages` используй поле `file`, а не `file_path`. После validation исправляй только реально оставшиеся ошибки, не перезаписывай все страницы.
