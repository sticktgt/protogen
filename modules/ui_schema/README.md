# UI Schema

Модуль хранения, просмотра, ручного редактирования и AI-синхронизации логической UI-схемы прототипа.

## Основные возможности

- карта UI и структура выбранной страницы;
- корневые элементы приложения и главное меню;
- ручное создание и редактирование страниц и UI-элементов;
- связи требований с UI и связи между UI-объектами;
- отображение кодовых связей, созданных агентом генерации кода;
- синхронизация текущей или исходной UI-схемы с полным JSON-файлом требований по относительному пути внутри workspace;
- обязательная статистика, семантический перечень изменений и подробный визуальный diff объектов;
- журнал работы агента, счётчики LLM/tool-вызовов, токенов и времени;
- диагностический ZIP по каждому завершённому запуску для анализа ошибок и расхода ресурсов;
- настраиваемые пределы выполнения и остановка при их достижении;
- опциональный визуальный preview во вкладках карты и структуры;
- применение всего результата либо полное отклонение;
- перегенерация с комментарием аналитика;
- ZIP-снимок перед применением и простое восстановление предыдущей схемы;
- экспорт всех входных требований со связанными UI-компонентами;
- хранение ссылки на канонический внешний файл требований без локальной копии в `ui_schema/`;
- метрики качества many-to-many трассировки требований;
- взаимоисключающая классификация требований: прямая UI-трассировка, `cross_cutting_ui`, `no_ui` или `unclear`;
- фактическая итоговая сводка, рассчитанная backend, отдельно от необязательного комментария модели.

## Ограниченный агент синхронизации

MVP использует минимальный LangChain-agent, которому доступны только доменные инструменты UI Schema. Универсальный Deep Agents harness не применяется: его встроенные planning/filesystem/execute-инструменты создавали лишние LLM-циклы и конфликтовали с ограниченным workflow.

Нормальный цикл:

1. `load_synchronization_context` — один раз загрузить задачу, требования, текущую схему и каталог типов;
2. `write_ui_schema_core` — записать только изменённые app/schema/UI links;
3. `write_ui_schema_pages` — одним или максимум двумя вызовами записать только новые или изменяемые страницы;
4. `write_ui_schema_traceability` — записать requirement links и итоговый отчёт;
5. `validate_ui_schema_state` — нормализовать технические неточности, проверить результат и автоматически завершить запуск при `valid=true`.

Промпты находятся в `modules/ui_schema/agent/prompts/`; provider, model, base URL и API key берутся из LLM-настроек текущего пользователя. Диагностические копии входа сохраняются в сессии запуска, но агент не получает filesystem, shell, execute, glob, grep, `write_file`, `edit_file` или todo-инструменты.

## Данные

Канонические данные находятся в `<workspace>/ui_schema/`. Временные сессии и ZIP-снимки находятся в `<workspace>/.protoarchitect/ui_schema_agent/` и не являются частью схемы.

Минимальный шаблон нового workspace находится в `modules/ui_schema/init/`.

## Каталог типов UI-элементов

Единый каталог типов хранится в `modules/ui_schema/config.yaml` в секции `ui.element_types`. Backend и frontend используют один и тот же runtime-конфиг.

## Ограничения MVP

- одновременно выполняется одна задача на workspace;
- один запрос LLM ограничен таймаутом; весь запуск ограничен временем, числом LLM/tool-вызовов, токенами, повторяющимися одинаковыми tool calls и recursion limit;
- статистика токенов показывается, когда её возвращает LLM-провайдер;
- требования читаются по относительному пути внутри workspace; после принятия результата сохраняется только `requirements_source.json`, а не копия требований;
- если внешний файл изменился после генерации preview, применение блокируется до перегенерации;
- результат применяется только целиком;
- временный preview доступен только для чтения;
- автоматическая коррекция исправляет только структурные ошибки и ограничена настройкой `validation_retries`;
- `code_links.json` агент синхронизации не изменяет;
- `index.json` пересобирается детерминированным backend-кодом.


### Временные запуски AI-синхронизации

После применения, отклонения или отмены результата временные копии запуска удаляются. Для анализа сохраняются диагностический архив и компактная итоговая запись запуска.

### Ограниченный цикл агента

Агент загружает текущий контекст одним доменным tool call, а затем пишет данные тремя специализированными типами вызовов: core-документы, изменяемые страницы и трассировка требований с отчётом. Tool schema требует native JSON objects/arrays; корректные JSON-строки отдельных полей принимаются только как аварийная совместимость. Гигантский строковый snapshot больше не используется. Пропущенные существующие страницы, элементы и необязательные поля сохраняются backend автоматически. Агент может удалять только ошибочные страницы и элементы, созданные в текущем запуске; объекты базовой схемы защищены. Перед валидацией backend однозначно нормализует новые children у атомарного `table` и ссылочные ID, различающиеся только разделителями, записывая действия в диагностику. Успешная проверка завершает цикл без дополнительного вызова LLM; валидный результат на границе лимита также переводится в preview. Новая страница не может быть удалена, пока она зарегистрирована или используется связями. `index.json` агентом не записывается и пересобирается backend после завершения.

## Источник требований и preview изменений

Каноническая UI-схема хранит `requirements_source.json` с относительным путём к файлу другого модуля и связи в `mappings/requirement_ui_links.json`. Содержимое требований разрешается динамически для показа кода, названия, типов и статуса в карточке связи. Legacy-файл `requirements.json` используется только для чтения старых workspace и удаляется после принятой AI-синхронизации.

В визуальном preview страницы и элементы получают отметки `+`, `~` и `−`. Общий перечень изменений и вложенные группы по умолчанию свёрнуты; их можно раскрыть вручную и перейти к конкретному объекту. Карточка страницы показывает суммарные изменения страницы, вложенных элементов и связей; перечень можно раскрыть и перейти к конкретному объекту. Для выбранного объекта показываются изменённые поля, добавленные/удалённые связи и технические данные до/после. Удалённые объекты доступны отдельным списком. Связи сравниваются по семантическим конечным точкам, поэтому смена только технического `id` не считается удалением и добавлением.

После построения UI агент выполняет отдельный проход трассировки по всем требованиям. Комплексное требование может иметь несколько целей; preview отдельно показывает требования, связанные только со страницами, с конечными элементами и с несколькими целями. Каждое требование получает ровно один итоговый статус: прямые UI-links, `cross_cutting_ui`, `no_ui` или `unclear`. Python не определяет семантику требований, а проверяет только полноту, отсутствие пересечений и совместимость статуса со связями. Свободный `agent_note` показывается отдельно, а основная сводка формируется backend из фактического diff и классификаций.

- `table` keeps explicit `table_column` children; legacy generated `text` columns are retyped without deleting their data or links.
