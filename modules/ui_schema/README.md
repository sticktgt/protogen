# UI Schema

Модуль хранит логическую UI-схему прототипа, позволяет редактировать её вручную и синхронизировать с полным текущим набором требований.

## Основные возможности

- страницы, корневые элементы приложения и дерево UI-элементов;
- связи требований с UI, связи между UI-объектами и отображение кодовых связей;
- синхронизация существующей или исходной схемы с JSON-файлом требований из workspace;
- preview изменений, статистика, объектный и построчный diff;
- применение результата целиком, отклонение и перегенерация с комментарием;
- диагностический ZIP с входом, снимками схемы, этапами pipeline и расходом LLM;
- ZIP-снимки схемы перед применением и восстановление последнего снимка;
- экспорт требований с итоговой UI-трассировкой.

## Управляемый pipeline

Синхронизация выполняется фиксированным backend-конвейером. Модель не выбирает следующий инструмент, не поддерживает историю автономного агента и не управляет стадиями.

1. **Анализ требований.** Backend механически делит требования по исходному порядку. Каждый изолированный LLM-вызов возвращает семантический разбор только своей группы.
2. **Проектирование и применение.** Группы требований последовательно сопоставляются с фактической текущей схемой. Модель формирует полные решения и один транзакционный пакет группы. После успешного применения следующий пакет видит уже обновлённую схему и может переиспользовать объекты, обновлять метаданные страниц или расширять существующую структуру.
3. **Техническое восстановление.** Отклонённый пакет полностью откатывается и передаётся модели на исправление в пределах настроенного числа попыток в том же ограниченном контексте.
4. **Независимый аудит.** Свежие изолированные вызовы проверяют только требования `direct_ui` по компактным структурам заявленных целей и связанным UI-переходам, возвращая только реальные дефекты.
5. **Точечная коррекция.** Дефекты и отсутствующие цели исправляются ограниченными группами requirement ID и отдельными транзакционными пакетами.
6. **Структурная проверка.** Backend сравнивает base/working и собирает локальные кандидаты: пустые или опустошённые контейнеры, подозрительное размещение, self-navigation, несколько навигационных целей одного источника и созданные целевые страницы без входящей навигации. Кандидаты не меняют схему и выводятся как предупреждения для ручной проверки.
7. **Экспорт и validation.** Backend механически формирует совместимые `mappings/requirement_ui_links.json` и `agent_report.json`, затем выполняет структурную проверку и готовит preview.

Backend не определяет смысл требования, UI-эффект, классификацию, подходящую цель, состав интерфейса или статус реализации. Он только оркестрирует этапы, проверяет структурированный формат, ID, типы, scope, родителей и ссылки, транзакционно применяет операции и сохраняет результат.

Промпты ролей находятся только в `modules/ui_schema/agent/prompts/`. Размеры групп, число попыток, имена prompt-файлов и output tools находятся только в `modules/ui_schema/config.yaml`.

## Синхронизация существующей схемы

Выбранный файл считается полным текущим набором требований. На этапе проектирования модель получает текущие страницы, элементы, UI-связи и прежнюю requirement-трассировку. Она может:

- связать требование с уже подходящим объектом;
- дополнить существующий объект без смены его ID и родителя;
- создать отсутствующую страницу или элемент;
- обновить название и описание существующей страницы;
- добавить явную UI-навигацию;
- оставить объект без изменений, когда схема уже достаточна.

Пакеты предыдущих групп уже применены и не повторяются. Отсутствующий requirement ID удаляет прежнюю requirement-связь из временного результата, но исходный UI-объект автоматически не удаляется. Структурные кандидаты после генерации только показываются как предупреждения и не изменяют UI-схему. Прежние связи отсутствующих требований показываются в `manual_review.json`.

## Данные

Канонические данные находятся в `<workspace>/ui_schema/`. Временные сессии, диагностика и снимки находятся в `<workspace>/.protoarchitect/ui_schema_agent/` и не являются частью схемы.

Минимальный шаблон нового workspace находится в `modules/ui_schema/init/`.

Каталог типов UI-элементов и все параметры pipeline хранятся в `modules/ui_schema/config.yaml`.

## Ограничения текущей версии

- одновременно выполняется одна синхронизация на workspace;
- один LLM-запрос и весь запуск ограничены временем, числом вызовов и токенами;
- результат применяется только целиком, preview доступен только для чтения;
- `code_links.json` pipeline не изменяет;
- `index.json` пересобирается backend-кодом;
- автоматическое удаление устаревших UI-объектов не выполняется;
- UI-схема описывает логическую структуру, а не конкретный frontend-фреймворк и не полное поведение приложения;
- качество результата оценивается как минимально достаточное представление обязательных пользовательских результатов, без требования промышленной полноты.

## Классификация требований

Каждый текущий requirement ID получает ровно один итог:

- прямая UI-трассировка;
- `cross_cutting_ui`;
- `no_ui`;
- `unclear`.

Для прямых связей модель также выбирает `planned`, `in_progress` или `implemented`. Backend проверяет полноту и техническую согласованность результата, но не выводит классификацию из текста требований.
