# AGENTS.md — модуль `ui_schema`

Документ предназначен для LLM-агентов и разработчиков, которые дорабатывают модуль `ui_schema` в проекте ProtoArchitect.

## 1. Назначение модуля

`ui_schema` — модуль работы со схемой UI будущего web-прототипа.

Модуль хранит, отображает и редактирует логическую схему интерфейса прототипа:

- страницы прототипа;
- корневые элементы приложения;
- главное меню;
- элементы страниц;
- модальные окна;
- связи между UI-объектами;
- связи требований с UI;
- связи UI с файлами кода прототипа.

Модуль не генерирует код прототипа и не реализует бизнес-поведение интерфейса. Он описывает структуру UI на уровне, пригодном для аналитика и для последующей генерации кода.

## 3. Документы модуля

Перед существенной доработкой модуля прочитать:

```text
modules/ui_schema/README.md
modules/ui_schema/docs/STORAGE.md
backend/modules/ui_schema/API.md
modules/ui_schema/api.openapi.yaml
modules/ui_schema/interop.yaml
```

Назначение документов:

- `README.md` — краткое описание модуля.
- `docs/STORAGE.md` — текущая структура файлов UI-схемы в workspace.
- `backend/modules/ui_schema/API.md` — краткое описание backend API модуля.
- `api.openapi.yaml` — машинно-читаемая документация API.
- `interop.yaml` — точки сопряжения модуля с другими модулями.

Если меняется структура хранения или API, обновить соответствующие документы модуля. Общие документы приложения менять только при изменении общих правил проекта.

## 4. Рабочие данные модуля в workspace

Для каждого workspace модуль использует папку:

```text
<workspace>/ui_schema/
```

Актуальная структура:

```text
ui_schema/
  app.json
  schema.json
  index.json
  links.json
  code_links.json
  mappings/
    requirement_ui_links.json
  requirements.json
  pages/
    <page_id>.json
```

`requirements.json` сейчас используется как локальный источник требований для демонстрации и ручной трассировки. Модуль `ui_schema` не должен редактировать требования как бизнес-данные. Основная ссылка на требование идет по `requirements[].id`.

## 5. Init-шаблон

Файлы для инициализации нового workspace находятся в:

```text
modules/ui_schema/init/
```

`init/` должен содержать только минимальную пустую структуру, необходимую для начала работы. Не добавлять туда демонстрационную банковскую схему, демо-страницы, демо-связи или реальные требования.

Демо-данные допустимы только в конкретном workspace, например:

```text
data/workspaces/ws_demo/ui_schema/
```

## 6. Основные файлы хранения

### `app.json`

Корневое описание приложения-прототипа и root UI-элементов.

Используется для:

- названия схемы;
- описания схемы;
- корневых элементов приложения;
- главного меню.

Главное меню хранится как root element типа `main_menu`.

### `schema.json`

Реестр страниц UI-схемы.

Каждая страница имеет отдельный файл в `pages/`.

### `pages/<page_id>.json`

Один файл — одна страница.

Правило имени файла:

```text
<page_id>.json
```

Пример:

```text
cards.block.json
payments.transfer.json
```

Файл страницы содержит:

- `id`;
- `title`;
- `description`;
- `elements`.

Не добавлять в страницу поля `route` и `layout`, если это специально не согласовано. Текущее решение: маршрут, layout и поведение не являются частью редактируемой UI-схемы первой версии.

### `links.json`

Связи между UI-объектами:

- пункт меню → страница;
- кнопка/ссылка/карточка → страница;
- кнопка/ссылка/карточка → модальное окно.

### `mappings/requirement_ui_links.json`

Связи требований с UI-объектами:

- требование → страница;
- требование → элемент;
- требование → пункт меню, если нужно связать требование с доступом через меню.

### `code_links.json`

Связи UI-объектов с файлами кода прототипа.

На текущем этапе ссылки на код только отображаются. Редактирование и создание таких ссылок через UI не является основной функцией модуля и может быть выполнено позже модулем генерации кода.

### `index.json`

Компактный индекс схемы.

Индекс должен пересобираться из основных файлов схемы. Не считать его основным источником истины.

## 7. Типы UI-элементов

Типы делятся на групповые и атомарные.

Групповые типы могут содержать дочерние элементы:

```text
section
form
filter_panel
toolbar
details_panel
tabs
modal
wizard
grid
table_with_actions
card
list
main_menu
menu_group
```

Атомарные типы не должны содержать дочерние элементы:

```text
text
image
input
password
textarea
select
checkbox
radio
button
link
table
badge
date_picker
file_upload
menu_item
```

Правила меню:

- `main_menu` может содержать `menu_group` и `menu_item`;
- `menu_group` может содержать `menu_item`;
- `menu_item` ведет на страницу через запись в `links.json`;
- меню не содержит страницы как дочерние элементы.

Переходы на страницы допустимы только для типов, которые логически могут быть источником перехода:

```text
menu_item
button
link
card
```

## 8. UI модуля

Основные вкладки:

```text
Карта UI
Структура страницы
```

### Карта UI

Показывает:

- root elements приложения;
- страницы;
- основные элементы страниц;
- признак включения страницы в меню через связи из `links.json`.

Клик по странице должен открывать вкладку `Структура страницы` и выбирать страницу. Клик по элементу страницы должен открывать вкладку `Структура страницы` и выбирать элемент.

### Структура страницы

Показывает:

- список страниц;
- структуру элементов выбранной страницы;
- root elements приложения;
- редактор выбранной страницы, root element или элемента.

Для страницы и элемента доступны вкладки редактора:

```text
Поля
Требования
Связи
Код
```

Добавление вложенного элемента показывать только на вкладке `Поля`.

Для атомарных элементов добавление вложенного элемента не показывать.

Страницу с вложенными элементами удалять нельзя. Сначала нужно удалить элементы страницы.

Групповой элемент с вложенными элементами удалять нельзя. Сначала нужно удалить дочерние элементы.

### JSON-представление

Не добавлять техническую вкладку с JSON, если это специально не запрошено. Модуль должен показывать схему через поля и структурные представления.

## 9. Backend-правила доработки

Backend API находится в:

```text
backend/modules/ui_schema/api.py
```

Реальную работу выносить в небольшие файлы по ответственности:

```text
storage.py
app_ops.py
page_ops.py
element_ops.py
link_ops.py
ui_link_ops.py
index_builder.py
summary.py
tree.py
```

Не раздувать `api.py` и `service.py`.

Рекомендуемое разделение:

- `api.py` — маршруты FastAPI;
- `schemas.py` — Pydantic-модели;
- `storage.py` — чтение и запись JSON-файлов;
- `app_ops.py` — операции с `app.json`;
- `page_ops.py` — операции со страницами;
- `element_ops.py` — операции с элементами;
- `link_ops.py` — связи требований и кода;
- `ui_link_ops.py` — связи UI-объектов между собой;
- `index_builder.py` — пересборка `index.json`;
- `summary.py` — агрегированная выдача для frontend;
- `tree.py` — поиск и обход элементов.

После операций, меняющих структуру схемы, пересобирать `index.json`.

## 10. Frontend-правила доработки

Frontend модуля находится в:

```text
frontend/modules/ui_schema/
```

Не создавать больших JS-файлов. Разделять код по функциям:

```text
api.js
state.js
main.js
render-map.js
render-structure.js
page-editor.js
element-editor.js
element-fields-tab.js
element-add-panel.js
element-requirements-tab.js
element-relations-tab.js
element-code-tab.js
html-utils.js
```

Общие правила:

- API-вызовы держать в `api.js`;
- состояние выбранной вкладки, страницы и элемента — в `state.js`;
- рендер карты UI — в `render-map.js`;
- рендер структуры — в `render-structure.js`;
- редактирование страницы — в `page-editor.js`;
- редактирование элемента — в файлах `element-*.js`;
- не вставлять большие HTML-строки в несвязанные файлы;
- не добавлять JSON-редактор, если это специально не требуется.

## 11. Требования и трассировка

Связи требований с UI хранятся в:

```text
ui_schema/mappings/requirement_ui_links.json
```

Каждая связь должна ссылаться на `requirements[].id`.

Для страницы и элемента на вкладке `Требования` показывать:

- список связанных требований;
- статус реализации связи;
- кнопку отвязки;
- кнопку перехода к требованию.

Переход к требованию может быть заглушкой, пока нет модуля требований.

Форма создания связи должна открываться только по кнопке `Связать с требованием` и скрываться после сохранения или отмены.

## 12. Связи UI-объектов

Связи между UI-объектами хранятся в:

```text
ui_schema/links.json
```

Поддерживаемые отношения текущей версии:

```text
navigates_to
opens_modal
```

Допустимые примеры:

```text
menu_item -> page
button -> page
link -> page
card -> page
button -> modal
```

Не добавлять связи перехода для `input`, `password`, `checkbox`, `text`, `form` и других типов, которые не являются источниками перехода.

## 13. Кодовые связи

Связи UI с файлами кода хранятся в:

```text
ui_schema/code_links.json
```

На вкладке `Код` показывать:

- тип файла;
- относительный путь;
- кнопку `Открыть`.

Кнопка `Открыть` может быть заглушкой, пока нет модуля работы с кодом.

На текущем этапе не добавлять ручное создание файлов кода через UI модуля `ui_schema`.

## 14. Что не менять без отдельного решения

Не менять без отдельного согласования:

```text
структуру workspace за пределами ui_schema/;
ядро приложения;
модель авторизации;
общие системные меню приложения;
формат пользовательских настроек;
текущий принцип app.json + schema.json + pages/*.json + links.json;
отсутствие JSON-вкладки в UI.
```

## 15. Проверки после изменений

После изменения backend:

```bash
python -m compileall backend/modules/ui_schema
```

После изменения frontend:

```bash
node --check frontend/modules/ui_schema/js/*.js
```

Минимальные ручные проверки:

```text
открывается модуль ui_schema;
открывается Карта UI;
открывается Структура страницы;
можно выбрать страницу;
можно выбрать элемент;
можно добавить элемент в групповой элемент;
нельзя добавить дочерний элемент в атомарный элемент;
нельзя удалить страницу с элементами;
нельзя удалить групповой элемент с дочерними элементами;
можно связать требование с элементом;
можно отвязать требование;
видны связи UI-объектов;
видны кодовые связи, если они есть.
```

## 16. Правила для LLM-агента

При доработке модуля:

1. Сначала определить, изменяется backend, frontend, структура хранения или документация.
2. Если меняется структура хранения, обновить `modules/ui_schema/docs/STORAGE.md`.
3. Если меняется API, обновить `backend/modules/ui_schema/API.md` и `modules/ui_schema/api.openapi.yaml`.
4. Если меняются точки сопряжения с другими модулями, обновить `modules/ui_schema/interop.yaml`.
5. Не добавлять демо-данные в `modules/ui_schema/init/`.
6. Не менять ядро приложения без явного требования.
7. Не создавать большие JS/Python-файлы.
8. Не добавлять фреймворк-специфичные поля UI-схемы без отдельного решения.
9. Не описывать поведение прототипа в UI-схеме, если это должно быть требованием.
10. Сохранять UI-схему понятной аналитику и пригодной для последующей генерации кода.
