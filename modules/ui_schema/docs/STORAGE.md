# UI Schema Storage

Документ описывает текущую структуру хранения данных модуля `ui_schema`.

UI-схема описывает логическую структуру web-интерфейса прототипа: страницы, элементы интерфейса, корневое меню, связи между UI-объектами, связи с требованиями и связи с файлами кода прототипа.

## 1. Расположение данных

Для каждого workspace данные UI-схемы хранятся в папке:

```text
<workspace>/ui_schema/
```

Текущая структура:

```text
ui_schema/
  app.json
  schema.json
  index.json
  links.json
  code_links.json
  requirements_source.json
  pages/
    <page_id>.json          # создается при добавлении страницы
  mappings/
    requirement_ui_links.json
  exports/
    requirements_ui/
      <run_id>.json         # экспорт принятой AI-синхронизации
```

Шаблон начальных данных для нового workspace находится в модуле:

```text
modules/ui_schema/init/
```

При создании нового workspace содержимое `modules/ui_schema/init/` копируется в:

```text
<workspace>/ui_schema/
```

Шаблон `modules/ui_schema/init/` содержит только минимальный набор пустых файлов для дальнейшего заполнения. Он не содержит демонстрационных страниц, элементов, связей и требований. Демо-структура для проверки интерфейса хранится отдельно в `data/workspaces/ws_demo/ui_schema/`.

## 2. Идентификаторы

Идентификаторы должны быть стабильными и пригодными для ссылок между файлами.

Рекомендуемый формат:

```text
<domain>.<object>
<domain>.<object>.<child>
```

Примеры:

```text
auth.login
cards.block
cards.block.form
cards.block.submit
app.main_menu.products.accounts
```

Для страницы `page_id` должен совпадать с именем файла страницы без расширения:

```text
page_id: cards.block
file: pages/cards.block.json
```

## 3. Типы UI-элементов

Типы UI-элементов являются логическими. Они не задают конкретный frontend-фреймворк, компонентную библиотеку, CSS-классы или верстку.

### 3.1. Общие поля элемента

Элемент UI имеет структуру:

```json
{
  "id": "cards.block.form",
  "type": "form",
  "label": "Форма блокировки карты",
  "description": "Поля для выбора карты и причины блокировки",
  "purpose": "Сбор параметров блокировки",
  "children": []
}
```

Поля:

| Поле | Обязательность | Описание |
|---|---:|---|
| `id` | да | Уникальный идентификатор элемента внутри UI-схемы. |
| `type` | да | Тип элемента из поддерживаемого перечня. |
| `label` | да | Отображаемое название элемента. |
| `description` | нет | Описание элемента для аналитика и модели. |
| `purpose` | нет | Назначение элемента. |
| `children` | для групповых | Вложенные элементы. Используется только у групповых элементов. |

### 3.2. Групповые элементы

Групповой элемент может содержать вложенные элементы.

| Тип | Описание |
|---|---|
| `section` | Логический раздел страницы. |
| `form` | Форма ввода данных. |
| `filter_panel` | Панель фильтров. |
| `toolbar` | Панель действий, кнопок или команд. |
| `details_panel` | Панель детальной информации. |
| `tabs` | Группа вкладок или разделов. |
| `modal` | Модальное окно с собственными вложенными элементами. |
| `wizard` | Пошаговая форма или сценарий. |
| `grid` | Логическая область с несколькими блоками. |
| `table_with_actions` | Таблица с действиями. |
| `table` | Таблица данных, содержащая только дочерние элементы `table_column`. |
| `card` | Карточка, содержащая элементы или информацию. |
| `list` | Список элементов или ссылок. |
| `main_menu` | Корневое меню приложения. Используется только в `app.json`. |
| `menu_group` | Группа пунктов меню. Используется только внутри `main_menu`. |

Правила для меню:

```text
main_menu может содержать menu_group и menu_item.
menu_group может содержать menu_item.
menu_item не содержит дочерних элементов.
```


Правила для таблиц:

```text
table может содержать только table_column.
table_column не содержит дочерних элементов.
Требования к явно перечисленным колонкам могут связываться непосредственно с table_column.
```

### 3.3. Атомарные элементы

Атомарный элемент не содержит вложенные элементы.

| Тип | Описание |
|---|---|
| `text` | Текстовый элемент. |
| `image` | Изображение или логотип. |
| `input` | Однострочное поле ввода. |
| `textarea` | Многострочное поле ввода. |
| `select` | Выбор значения из списка. |
| `checkbox` | Флаг да/нет. |
| `radio` | Выбор одного варианта из набора. |
| `button` | Кнопка действия. |
| `link` | Ссылка или переход. |
| `table_column` | Колонка таблицы. Используется только внутри `table`. |
| `badge` | Метка, статус или небольшой индикатор. |
| `date_picker` | Поле выбора даты. |
| `file_upload` | Поле загрузки файла. |
| `menu_item` | Пункт меню. Используется только внутри `main_menu` или `menu_group`. |

## 4. Файлы UI-схемы

## 4.1. `app.json`

Файл описывает корневые элементы интерфейса прототипа.

Текущая основная роль файла — хранение главного меню.

Пример:

```json
{
  "id": "app",
  "title": "Банковский фронт-офис ФЛ",
  "description": "Корневые элементы прототипа: меню и общие области интерфейса.",
  "root_elements": [
    {
      "id": "app.main_menu",
      "type": "main_menu",
      "label": "Главное меню",
      "description": "Основная навигация прототипа",
      "children": [
        {
          "id": "app.main_menu.products",
          "type": "menu_group",
          "label": "Продукты",
          "children": [
            {
              "id": "app.main_menu.products.accounts",
              "type": "menu_item",
              "label": "Счета"
            }
          ]
        }
      ]
    }
  ]
}
```

Поля:

| Поле | Обязательность | Описание |
|---|---:|---|
| `id` | да | Идентификатор корневого объекта. Текущее значение: `app`. |
| `title` | да | Название прототипа. |
| `description` | нет | Описание прототипа или корневых элементов. |
| `root_elements` | да | Корневые UI-элементы приложения. |

Новый элемент массива `root_elements` создается, когда в UI-схему добавляется корневой элемент приложения. В текущей версии поддерживается корневое меню `main_menu`.

Пункты меню не содержат страницы. Связь пункта меню со страницей хранится в `links.json`.

## 4.2. `schema.json`

Файл содержит общий реестр страниц UI-схемы.

Пример:

```json
{
  "schema_version": "0.1",
  "application": {
    "name": "Generated Prototype",
    "description": "Описание UI-схемы прототипа"
  },
  "pages": [
    {
      "id": "cards.block",
      "title": "Блокировка карты",
      "file": "pages/cards.block.json"
    }
  ]
}
```

Поля:

| Поле | Обязательность | Описание |
|---|---:|---|
| `schema_version` | да | Версия структуры UI-схемы. |
| `application.name` | да | Техническое или рабочее название прототипа. |
| `application.description` | нет | Описание UI-схемы. |
| `pages` | да | Реестр страниц. |

Элемент массива `pages`:

| Поле | Обязательность | Описание |
|---|---:|---|
| `id` | да | Идентификатор страницы. |
| `title` | да | Название страницы. |
| `file` | да | Относительный путь к файлу страницы. |

Новый элемент массива `pages` создается при добавлении новой страницы в UI-схему.

## 4.3. `pages/<page_id>.json`

Для каждой страницы создается отдельный файл:

```text
pages/<page_id>.json
```

Правило именования:

```text
page id: cards.block
file: pages/cards.block.json
```

Пример:

```json
{
  "id": "cards.block",
  "title": "Блокировка карты",
  "description": "Страница блокировки карты клиента",
  "elements": [
    {
      "id": "cards.block.form",
      "type": "form",
      "label": "Форма блокировки карты",
      "children": [
        {
          "id": "cards.block.card",
          "type": "select",
          "label": "Карта"
        },
        {
          "id": "cards.block.submit",
          "type": "button",
          "label": "Заблокировать карту"
        }
      ]
    },
    {
      "id": "cards.block.confirm_modal",
      "type": "modal",
      "label": "Подтверждение блокировки карты",
      "children": [
        {
          "id": "cards.block.confirm_text",
          "type": "text",
          "label": "Текст подтверждения"
        }
      ]
    }
  ]
}
```

Поля страницы:

| Поле | Обязательность | Описание |
|---|---:|---|
| `id` | да | Идентификатор страницы. Совпадает с `id` в `schema.json`. |
| `title` | да | Название страницы. |
| `description` | нет | Описание назначения страницы. |
| `elements` | да | Список элементов верхнего уровня страницы. |

Новый элемент массива `elements` создается, когда на страницу добавляется новый элемент верхнего уровня.

Новый дочерний элемент создается внутри массива `children` группового элемента.

Страница не хранит route, layout и правила поведения. Эти данные в текущей версии не входят в UI-схему.

## 4.4. `links.json`

Файл хранит связи между UI-объектами.

Пример связи пункта меню со страницей:

```json
{
  "links": [
    {
      "id": "link.menu.cards.block",
      "source_type": "ui_element",
      "source_id": "app.main_menu.cards.block",
      "target_type": "page",
      "target_id": "cards.block",
      "relation": "navigates_to"
    }
  ]
}
```

Пример связи кнопки с модальным окном:

```json
{
  "links": [
    {
      "id": "link.cards.block.confirm_modal",
      "source_type": "ui_element",
      "source_id": "cards.block.submit",
      "target_type": "ui_element",
      "target_id": "cards.block.confirm_modal",
      "relation": "opens_modal"
    }
  ]
}
```

Поля элемента массива `links`:

| Поле | Обязательность | Описание |
|---|---:|---|
| `id` | да | Идентификатор связи. |
| `source_type` | да | Тип источника: `page` или `ui_element`. |
| `source_id` | да | Идентификатор источника. |
| `target_type` | да | Тип цели: `page` или `ui_element`. |
| `target_id` | да | Идентификатор цели. |
| `relation` | да | Тип связи. |

Новый элемент массива `links` создается для каждой отдельной связи между UI-объектами.

Текущие используемые значения `relation`:

| Значение | Описание |
|---|---|
| `navigates_to` | Источник ведет на страницу. |
| `opens_modal` | Источник открывает модальное окно. |

Включение страницы в меню определяется связью:

```text
menu_item -> page
relation: navigates_to
```

## 4.5. `mappings/requirement_ui_links.json`

Файл хранит связи требований с объектами UI-схемы.

Сами требования принадлежат внешнему модулю и не копируются в каноническую папку `ui_schema/`. Источник задаётся файлом `requirements_source.json`, а связи используют стабильное поле внешнего требования:

```text
requirements[].id
```

Пример:

```json
{
  "links": [
    {
      "id": "link_001",
      "requirement_id": "REQ-0422",
      "target_type": "page",
      "target_id": "cards.block",
      "relation": "implemented_by",
      "implementation_status": "planned"
    },
    {
      "id": "link_002",
      "requirement_id": "REQ-0422",
      "target_type": "ui_element",
      "target_id": "cards.block.form",
      "relation": "implemented_by",
      "implementation_status": "in_progress"
    }
  ]
}
```

Поля элемента массива `links`:

| Поле | Обязательность | Описание |
|---|---:|---|
| `id` | да | Идентификатор связи. |
| `requirement_id` | да | Ссылка на `requirements[].id`. |
| `target_type` | да | Тип UI-объекта: `page` или `ui_element`. |
| `target_id` | да | Идентификатор страницы или UI-элемента. |
| `relation` | да | Тип связи требования с UI-объектом. |
| `implementation_status` | да | Статус реализации связи. |

Новый элемент массива `links` создается для каждой связи требования с отдельной страницей или отдельным UI-элементом.

Текущие используемые значения `relation`:

| Значение | Описание |
|---|---|
| `implemented_by` | UI-объект реализует требование. |
| `supports` | UI-объект поддерживает выполнение требования. |
| `triggers` | UI-объект запускает действие, связанное с требованием. |
| `starts_flow` | UI-объект начинает пользовательский сценарий. |

Текущие используемые значения `implementation_status`:

| Значение | Описание |
|---|---|
| `planned` | Реализация запланирована. |
| `in_progress` | Реализация находится в работе. |
| `implemented` | Реализация выполнена. |

## 4.6. `code_links.json`

Файл хранит связи UI-объектов с файлами кода прототипа.

В текущей версии связь с кодом отображается в UI, но переход к файлу кода не реализован.

Актуальный формат записи:

```json
{
  "links": [
    {
      "id": "code_el_cards_block_form",
      "target_type": "ui_element",
      "target_id": "cards.block.form",
      "kind": "frontend_component",
      "path": "src/components/cards/CardBlockForm.jsx"
    }
  ]
}
```

Поля элемента массива `links`:

| Поле | Обязательность | Описание |
|---|---:|---|
| `id` | да | Идентификатор связи. |
| `target_type` | да | Тип UI-объекта: `page` или `ui_element`. |
| `target_id` | да | Идентификатор страницы или UI-элемента. |
| `kind` | да | Тип файла или участка кода. |
| `path` | да | Относительный путь к файлу кода прототипа. |

Новый элемент массива `links` создается для каждой связи UI-объекта с отдельным файлом кода.

Текущие используемые значения `kind`:

| Значение | Описание |
|---|---|
| `frontend_page` | Файл страницы frontend-прототипа. |
| `frontend_component` | Файл компонента frontend-прототипа. |
| `frontend_file` | Обобщенный frontend-файл. |

Добавление связей с кодом через UI в текущей версии не реализовано. Такие связи предполагается создавать при генерации кода.

## 4.7. `index.json`

Файл содержит производный индекс UI-схемы.

`index.json` используется для быстрого отображения и поиска по схеме. Файл пересобирается из `schema.json`, `app.json`, `pages/*.json`, `links.json` и `mappings/requirement_ui_links.json`.

Пример:

```json
{
  "pages": [
    {
      "id": "cards.block",
      "title": "Блокировка карты",
      "summary": "Страница блокировки карты клиента",
      "requirement_ids": ["REQ-0422"],
      "main_elements": [
        {
          "id": "cards.block.form",
          "type": "form",
          "label": "Форма блокировки карты"
        }
      ],
      "incoming_links": [
        {
          "id": "link.menu.cards.block",
          "source_type": "ui_element",
          "source_id": "app.main_menu.cards.block",
          "target_type": "page",
          "target_id": "cards.block",
          "relation": "navigates_to"
        }
      ]
    }
  ],
  "root_elements": [
    {
      "id": "app.main_menu",
      "type": "main_menu",
      "label": "Главное меню"
    }
  ]
}
```

Поля верхнего уровня:

| Поле | Описание |
|---|---|
| `pages` | Краткое описание страниц. |
| `root_elements` | Краткое описание корневых элементов приложения. |

`index.json` не редактируется вручную.

## 4.8. `requirements_source.json`

Файл хранит ссылку на канонический источник требований в другом модуле workspace. Сами требования в папку `ui_schema/` не копируются.

Пример:

```json
{
  "type": "workspace_file",
  "path": "requirements/requirements.json",
  "sha256_at_sync": "..."
}
```

Поля:

| Поле | Обязательность | Описание |
|---|---:|---|
| `type` | да | Текущий поддерживаемый тип: `workspace_file`. |
| `path` | да после первой принятой синхронизации | Путь к файлу требований относительно корня workspace. |
| `sha256_at_sync` | нет | Контрольная сумма источника на момент принятой синхронизации. Используется для предупреждения об изменении внешнего файла. |

Backend разрешает содержимое требований при чтении UI-схемы. Поэтому карточки связей могут показывать код, название, типы и статус требования, не сохраняя локальную копию. Если внешний файл недоступен, связи не удаляются: UI показывает `requirement_id` и предупреждение об источнике.

Правила изменения внешнего источника:

- изменение текста при сохранении `id` не разрывает связь; при следующем чтении показывается новая редакция;
- новое требование появляется как несвязанное и не меняет UI автоматически;
- удалённое требование оставляет неразрешённую связь до ручного решения или следующей синхронизации;
- изменение `id` рассматривается как удаление старого и появление нового требования;
- если файл изменился между запуском AI и применением preview, применение блокируется и требуется перегенерация на актуальном источнике.

Для совместимости старый `ui_schema/requirements.json` может читаться как legacy-источник только если `requirements_source.json` ещё отсутствует. Если файл ссылки уже существует, legacy-копия не используется и автоматически удаляется при инициализации или первом открытии модуля. После принятой AI-синхронизации сохраняется только `requirements_source.json`.

## 4.9. `exports/requirements_ui/<run_id>.json`

После принятия результата AI-синхронизации создаётся машинно-читаемый экспорт для модуля требований. Экспорт содержит все требования из входного файла и для каждого требования:

- полный исходный объект требования;
- взаимоисключающий результат `linked`, `cross_cutting_ui`, `no_ui`, `unclear` или аварийный `unclassified`;
- список связанных страниц и UI-элементов;
- пояснение и область действия для `cross_cutting_ui`, `no_ui` и `unclear`;
- фактическую статистику трассировки, рассчитанную backend по links и классификациям.

Файл является результатом обмена между модулями. Основным источником связей внутри UI-схемы остаётся `mappings/requirement_ui_links.json`.

## 5. Создание новых элементов данных

### 5.1. Новая страница

При создании страницы создаются или изменяются файлы:

```text
schema.json
pages/<page_id>.json
index.json
```

В `schema.json` добавляется элемент массива `pages`.

Создается новый файл:

```text
pages/<page_id>.json
```

Пример нового файла страницы:

```json
{
  "id": "reports.statement",
  "title": "Выписка по счету",
  "description": "Страница формирования выписки по счету",
  "elements": []
}
```

### 5.2. Новый элемент страницы

При создании элемента верхнего уровня страницы новый объект добавляется в:

```text
pages/<page_id>.json -> elements[]
```

При создании вложенного элемента новый объект добавляется в:

```text
pages/<page_id>.json -> elements[].children[]
```

### 5.3. Новый элемент меню

При создании главного меню или группы меню новый объект добавляется в:

```text
app.json -> root_elements[] / children[]
```

Пункт меню создается как `menu_item`. Связь пункта меню со страницей создается отдельно в `links.json`.

### 5.4. Новая связь между UI-объектами

При создании связи между UI-объектами новый объект добавляется в:

```text
links.json -> links[]
```

### 5.5. Новая связь требования с UI

При создании связи требования со страницей или элементом новый объект добавляется в:

```text
mappings/requirement_ui_links.json -> links[]
```

### 5.6. Новая связь UI с кодом

Связь UI с файлом кода создается в:

```text
code_links.json -> links[]
```

В текущей версии UI отображает эти связи, но не создает их вручную.

## 6. Временные данные AI-синхронизации

Временные сессии и архивы не хранятся внутри `ui_schema/`. Они располагаются в workspace:

```text
<workspace>/.protoarchitect/ui_schema_agent/
  active_run.json
  initial/ui_schema.zip
  runs/<run_id>/
    input/
      requirements.json
      requirements.agent.json
      ui_schema_context.json
      task.json
    reference/
    base/ui_schema/
    working/ui_schema/
    scratch/
    result/
      agent_report.json  # agent_note и взаимоисключающие cross_cutting_ui/no_ui/unclear
      agent_completion.json
      validation.json
      changes.json
      requirements_ui_result.json
  history/<snapshot_id>/
    ui_schema.zip
    metadata.json
```

`requirements.agent.json` и `ui_schema_context.json` являются компактными read-only представлениями входных данных для сокращения числа LLM/tool-итераций. Ограниченный LangChain-agent изменяет только `working/ui_schema/` через доменные инструменты. При принятии результата создаётся ZIP-снимок текущей схемы, после чего временная схема заменяет рабочую целиком. Архивирование выполняется Python-кодом без Git и без командной строки.

## 7. Ограничения текущей версии

1. UI-схема не описывает конкретную frontend-библиотеку или фреймворк.
2. UI-схема не хранит route и layout страниц.
3. UI-схема не описывает полное поведение интерфейса.
4. Связи с API и backend-функциями в текущей версии не реализованы.
5. Связи с файлами кода отображаются, но переход к файлу кода не реализован.
6. Добавление связей с кодом через UI не реализовано.
7. UI-схема хранит только `requirements_source.json` и связи по `requirement_id`; доступность внешнего источника контролируется отдельно.
8. Legacy-файл `requirements.json` поддерживается только для чтения старых workspace и удаляется после принятой синхронизации.
9. `index.json` является производным файлом и не редактируется вручную.
10. Удаление страницы с вложенными элементами запрещено до удаления ее элементов.
11. Удаление группового элемента с вложенными элементами запрещено до удаления дочерних элементов.
12. В текущей версии главное меню хранится в `app.json`; отдельный `navigation.json` не используется.

## Служебные данные наблюдения за агентом

Для каждого запуска во временной сессии дополнительно создаются:

```text
<workspace>/.protoarchitect/ui_schema_agent/runs/<run_id>/
  events.jsonl    # последовательный технический журнал
  metrics.json    # LLM/tool-вызовы, токены, пределы и последняя активность
```

Эти файлы не входят в каноническую UI-схему и не переносятся при применении результата. `events.jsonl` не хранит prompt, содержимое требований и внутренние рассуждения модели.
## Таблицы и канонические поля элементов

Каждый UI-элемент хранит непустой `label`. Поле `title` может присутствовать для совместимости, но не заменяет `label`; при приёме агентского результата backend может однозначно скопировать уже переданный `title`/`text` в `label`.

`table` является групповым элементом. Его непосредственными детьми могут быть `table_column`, а также явно предусмотренные требованиями действия `button` и `link`. `table_column` может быть источником UI-связи, например для колонки действий.

В `schema.json` ссылка на файл страницы хранится в поле `file`:

```json
{"id": "auth.login", "title": "Вход", "file": "pages/auth.login.json"}
```

Поле `file_path` не является каноническим и нормализуется в `file`.
